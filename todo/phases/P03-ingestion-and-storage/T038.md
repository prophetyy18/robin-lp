# T038 — Acquire and qualify the two-pool ten-million-block window

> Phase: `P03`
> Contract status: `OWNER_PLAN_EXTENSION_2026-09-18`

## Dependencies

T036, T037

## Outcome

two materially different pools are acquired and qualified over one window of at
least ten million blocks whose end is a pinned, finalized block: the already
pinned ZZZ/USDG reference pool, re-acquired in this window, and the Owner-pinned
second pool whose `PoolKey` and `Initialize` block are resolved and verified on
chain by this task.

This task produces a new dataset generation. The 2026-09-18 reference dataset
remains immutable historical evidence and is neither overwritten nor merged. The
second pool is what T042's "heterogeneous pools" acceptance and the product
delivery standard's "at least two materially different pool fixtures, one of them
native currency or nonzero hook" require; no other task produces it.

### Window rule (Owner decision 2026-09-18, delegated)

The window end is a **finalized** block, never `latest`:

- at run start, read the `finalized` tag from both qualified endpoints; the two
  must agree on block number and block hash, or the run fails closed with a
  reason code and acquires nothing;
- the window end is that block, pinned by number and hash into the run manifest,
  the T034 report and the evidence pack; a same-named range without a pinned end
  is not reproducible and is not accepted;
- the window start is `min(end - 10_000_000, Initialize block of each included
  pool)`;
- the start is extended below `end - 10_000_000` only when a pool's `Initialize`
  lies within 2,000,000 blocks of it. A pool whose `Initialize` lies further below
  is reported as `pool_init_outside_window` and is **excluded** from the qualified
  dataset rather than extending the window; extended and excluded pools are both
  named in the report.

## Deliverables

1. Second-pool resolution: a `PoolId`-filtered `Initialize` scan over the candidate
   window yielding the pool's `PoolKey` and `Initialize` block, the offline
   re-derivation check `keccak256(abi.encode(PoolKey)) == PoolId`, and — when the
   `Initialize` is not inside the window — the documented search bounds and the
   `pool_init_outside_window` outcome instead of a guessed value.
2. One qualified dataset per included pool over the same pinned window, each with
   its own data root and its own T034 machine report with `complete=true`, and with
   the T037 reconciliation check reporting agreement for every partition.
3. The reference pool re-acquired cold in this window, from its `Initialize` block
   under the window rule above, with the 2026-09-18 dataset left untouched.
4. Independent fidelity and state checks per pool: cross-endpoint sampled
   re-acquisition compared per `EventKey` by normalized content hash, and a
   block-pinned StateView spot check at the window end issued to an endpoint that
   can serve historical state at that depth, with golden values recorded.
5. Failure-path evidence against the real endpoints: `finalized` unavailable,
   the two endpoints disagreeing on `finalized`, a request wider than an
   endpoint's measured per-call capability, rate limiting, and budget exhaustion —
   each producing its documented reason code and never a false `complete=true`.
6. An operator runbook stating which endpoint carries the wide scan, which serves
   the sampled cross-validation and the historical-state read, the measured
   per-endpoint capability bounds those choices rely on, the pinned finalized end
   block, the resolved second-pool identity, and the per-pool data roots.

## Acceptance

- both included pools produce a T034 report with `complete=true`, every interval
  `successful` or `scanned_empty`, none `failed` or `cancelled`, and no
  unexplained gap;
- the second pool's `PoolId` re-derives exactly from the resolved `PoolKey`, and a
  mismatch halts the run rather than being reconciled by hand;
- the window end is a finalized block whose number and hash are recorded and were
  agreed by both qualified endpoints at run start; no `latest` read appears
  anywhere in the acquisition or the state spot check;
- each included pool's dataset contains that pool's `Initialize` event, so the
  cold-start coverage rule holds for every pool in the dataset; a pool excluded
  under the window rule is reported as `pool_init_outside_window` with the gap
  size recorded;
- `event_index` and Parquet agree per partition for both pools under the T037
  reconciliation path, and the reference pool's row counts are compared against
  its own recorded baseline with any difference raised rather than explained away;
- sampled cross-endpoint windows agree per `EventKey` by normalized content hash
  for every sampled event; a window the second endpoint cannot serve is reported
  as blocked, never skipped and never replaced by re-reading the first endpoint;
- the runbook reproduces the run from a clean environment, and a re-run leaves the
  manifests, checkpoints and partition sets indistinguishable from the first run;
- the acquisition remains range-based: no per-block `eth_getLogs`, no per-block
  header fetch, no header fetch for a block with no pool event, and no `eth_call`
  during acquisition other than the explicitly enumerated block-pinned
  verification reads, whose count is recorded;
- logical RPC calls, HTTP requests, bytes, rows, provider units, storage size and
  elapsed time are reported per pool and in total, separately from header reads;
- if the second pool's `hooks` is not `0x0`, it is classified per T023 and its
  support level does not exceed `ingestion` until a T043-level evidence pack
  exists; the classification outcome is recorded;
- `pytest`, Ruff format/check and the strict type checker pass.

## Must not

- use `latest`, a non-finalized block, or a wall-clock-derived bound as the window
  end, or fall back to `latest` when a `finalized` tag is unavailable;
- overwrite, merge into, repair or delete the 2026-09-18 reference dataset, its
  partitions or its manifest;
- widen the window to chase a pool whose `Initialize` lies more than 2,000,000
  blocks below `end - 10_000_000`, or include such a pool in the qualified dataset;
- guess the second pool's `PoolKey`, fee, tickSpacing or hooks from its `PoolId`,
  from a symbol, or from another pool's bytecode;
- claim cross-endpoint agreement as independent-provider verification, or present
  sampled agreement as full-range verification;
- report `complete=true` while any partition's index and Parquet disagree, or while
  a reconciliation mismatch is open;
- model an unknown hook as a no-hook pool, or promote a pool beyond its
  classification;
- widen, swap or substitute the pinned reference pool, its `PoolId`, `PoolKey` or
  chain, or add a third pool or another chain.
