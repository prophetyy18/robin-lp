# T034 — Produce data-quality and completeness reports

> Phase: `P03`

## Dependencies

T032, T033

## Outcome

T034 owns the **data-quality and completeness reports** that decide
whether a downstream consumer is allowed to load a dataset. The
reports qualify ADR-010 routing, budget, and sampled A+B agreement as
part of dataset completeness. Downstream code consumes only
explicitly qualified datasets; a dataset without a passing T034
report is not qualified and must not be loaded.

The T034 report is the single source of truth that downstream code
reads before trusting it. Every reported reason code, manifest
checksum, capability snapshot, budget figure, sample comparison,
and infrastructure-correlation state is produced by T034 and
referenced by downstream code.

- T034 = data-quality and completeness reports with ADR-010 routing,
  budget, and sampled A+B agreement qualification;
- downstream code consumes only explicitly qualified datasets;
- `complete=true` is the qualification gate. `complete=false`,
  `complete=null`, or any absent qualification forces downstream
  consumers to refuse the dataset;
- the report's sampled A+B agreement is **cross-endpoint
  agreement**, not independent-provider agreement. Infrastructure
  independence is not claimed unless independent evidence exists
  (Decision 8).

## Deliverables

### Machine reports

A machine-readable report that records, at minimum:

- **range coverage** — committed block-range partitions, partition
  bounds (`start_block`, `end_block`), committed status per
  partition, and the gap status for blocks outside any committed
  partition;
- **block / hash gaps** — blocks requested but not covered; missing
  block hashes; blocks whose fetched hash disagrees with the
  block-pinned reference saved at scan time; blocks present in
  one provider's response but missing from the other provider's
  response for the same interval;
- **duplicate / misordered logs** — duplicate `EventKey`s
  `(chain_id, block_hash, tx_hash, log_index)` discovered within
  one interval or across overlapping intervals; logs whose
  `(block_number, transaction_index, log_index)` ordering violates
  the deterministic global order;
- **unknown pools** — `Initialize` logs whose `poolId` does not
  match any selected pool or whose pool is not in the registry;
- **decode errors** — raw logs that survived the schema-decode
  pipeline but whose typed body failed reconstruction against the
  pinned v4-core ABI artifact; the typed body mismatch must be
  named with the event name and the ABI field that failed;
- **impossible values** — decoded amounts that overflow the ABI
  width, signed deltas whose sign disagrees with the ABI
  definition, ticks outside the V4 tick range, liquidity values
  that disagree with the active-liquidity invariant, and any
  other value the protocol cannot produce;
- **stale endpoints** — endpoint aliases whose last successful
  retrieval is older than the staleness threshold, whose
  preflight-probed capability regressed below the planned
  capability, or whose measured cap no longer covers the
  requested interval;
- **metadata failures** — chain identity mismatch (chain ID,
  genesis hash, PoolManager address, StateView address) versus
  the pinned chain artifact; block-header reads that returned
  the wrong block hash; parent-hash inconsistencies; integer
  timestamp anomalies;
- **cross-provider / subgraph discrepancies** — any case where
  the same `EventKey` was observed by both endpoints with
  disagreeing normalized content, where one provider returned
  a log the other did not, or where the response size, request
  interval, or capability snapshot differs in a way that affects
  qualification;
- **reason codes** — every report row carries an explicit reason
  code (for example `range_coverage_gap`, `duplicate_event_key`,
  `unknown_pool`, `decode_error`, `impossible_value`,
  `stale_endpoint`, `metadata_failure`,
  `cross_provider_discrepancy`, `budget_exhausted`,
  `capability_regression`, `user_agent_rejected`,
  `cross_endpoint_sample_missing`,
  `cross_endpoint_sample_disagree`,
  `infrastructure_correlation_state_unrecorded`,
  `checkpoint_mismatch`, etc.). Reason codes are distinct and
  the report never collapses multiple distinct failure modes into a
  single counter.

### Human reports

A human-readable report that, at minimum:

- summarizes the dataset's qualification verdict (`true` / `false`)
  with the chain identity, the pool identifier, the start and end
  block, the checkpoint reference, the manifest checksum, the
  infrastructure-correlation state, and the timestamp at which
  the report was generated;
- lists every reason code raised, grouped by category, with the
  count and the highest-severity sample per category;
- surfaces the preflight/actual call budget, the endpoint
  capability snapshot, the provider-to-interval provenance, and
  the response/storage volume as separate named sections;
- surfaces the deterministic cross-provider sample selection
  with the compared block hashes and the compared log results;
- surfaces the recorded infrastructure-correlation state with the
  `cross_endpoint_agreement` phrasing and an explicit residual-
  risk callout when the state is not `evidenced_independent`;
- names the cold-start Initialize block (when applicable) or the
  qualified local checkpoint and the complete suffix (when
  applicable), and states whether the basis is satisfied.

### Preflight / actual call budget

The report records the call budget as a **paired preflight /
actual** ledger:

- **preflight** — the remaining call / compute-unit / time budget
  the run allocated per endpoint before any RPC traffic was sent.
  The preflight budget is sourced from operator injection at run
  start or from a provider usage API consulted before the scan
  begins; an unspecified or unobservable remaining budget is
  recorded as `remaining_budget_source =
  operator_injection_unknown` or `remaining_budget_source =
  provider_usage_api_unavailable` and is treated as a hard cap of
  zero;
- **actual** — the budget actually consumed per endpoint: logical
  RPC calls, HTTP requests / batches, response bytes, normalized
  rows, provider units when reported (for example Alchemy CU),
  elapsed time, and Parquet bytes written. The actual budget is
  split by endpoint alias and by partition;
- **deviation** — every deviation from the preflight plan is
  recorded separately: capability regression, observed limit
  lower than measured, observed Alchemy 10-block cap, Robinhood
  `User-Agent` 403, response-size overflow, rate-limit retries,
  provider failover events, budget overrun. Warning counts do not
  disappear inside aggregates; each deviation is a distinct row
  in the deviation ledger.

### Endpoint capability snapshot

A snapshot, recorded at run start, of each endpoint's measured
capability. The snapshot includes, per endpoint:

- alias, chain/deployment identity, supported finality tags,
  archive-state depth, accepted log range, latency, and probe
  block/hash;
- measured `eth_getLogs` capability (max blocks per request,
  observed response size, observed rate-limit headers);
- measured block-header read capability;
- the call / compute-unit / time budget allocated to this run;
- the remaining-budget source and bound.

The capability snapshot is persisted to durable storage before
the scan starts, so a crash at any later boundary still leaves
the recorded capability and budget for replay and for the next
run's planning.

### Provider-to-interval provenance

The report records, per interval, the provider that actually
served it, the failover path used (if any), the retry count, the
reason for any retry, the response size, the request interval,
and the durable-commit checksum. Provider failover does not
silently merge two partial responses into one supposedly complete
range; the provenance row identifies which provider's bytes the
interval was committed against.

### Response / storage volume

The report records, per run and per endpoint, response bytes
fetched, normalized rows produced, Parquet bytes written,
provider units when reported, and elapsed time. Calendar duration
alone is not a call-count input; logical RPC calls and HTTP
requests are recorded separately.

### Deterministic cross-provider sample selection (Decision 6)

The report records the deterministic cross-provider sample
selection that produced its required A+B comparisons. Sample
selection depends only on **PoolId**, **partition bounds**,
**EventKey**, and **manifest** — deterministic inputs only.
Sample selection never uses random number generation or wall
clock. The report names, for every required sample, the selection
inputs that chose it, so the same selection can be reproduced
from the manifest alone.

The selection rules, verbatim from Decision 6:

1. **Per run** — compare, across A and B:
   - chain ID;
   - genesis hash;
   - the block hash of the same fixed block;
   - PoolManager runtime code hash;
   - StateView runtime code hash.

2. **Per committed block-range partition** — compare, across A
   and B:
   - the opening 10-block window of the partition;
   - the trailing 10-block window of the partition.

3. **Per actually-observed event type in the dataset** —
   compare, across A and B:
   - the first 10-block window that contains the smallest
     `EventKey` of that event type. Identical windows are
     deduplicated.

4. **Per provider failover** — compare, across A and B:
   - the 10-block window immediately before the failover
     boundary;
   - the 10-block window immediately after the failover
     boundary. Overlapping or adjacent windows may be merged.
     If the original endpoint has not yet recovered, the
     data may be staged, but the dataset remains unqualified
     until the required comparison completes.

5. **Result-bearing requirement** — if the dataset contains
   any events:
   - at least one required A+B comparison must be
     **result-bearing** (it must include actual log results,
     not an all-empty array). All-empty capability samples
     may not substitute for result-bearing real-event
     comparisons.

`complete=true` is permitted only when **every required sample
agrees** across A and B **and** no other gap / error / budget
failure exists. Any missing required sample, any disagreeing
required sample, or any unresolved gap / error / budget failure
forces `complete=false` and blocks downstream qualification.

### Infrastructure-correlation evidence (Decision 8)

The report records the infrastructure-correlation evidence state
of the two endpoints as one of three enum values:

- `unknown_not_proven` — current evidence state. The two
  endpoints have been observed to agree on chain identity,
  blocks, runtime code, and real historical log results, but
  no evidence proves the underlying nodes, upstream data
  sources, or failure domains are independent;
- `known_correlated` — separate evidence has established that the
  two endpoints share operator, infrastructure, or upstream
  data sources. Correlated failure is then a recorded residual
  risk;
- `evidenced_independent` — separate auditable operational or
  infrastructure evidence has established the two endpoints
  are independent.

The current state is **`unknown_not_proven`**. The state must
not be left blank. When the state is `unknown_not_proven` or
`known_correlated`, the report must surface correlated failure
as an explicit residual risk.

The report describes the A+B comparison result as
**`cross_endpoint_agreement`**. The report must **not** describe
the result as `independent_provider_agreement`. The
`independent_provider_agreement` wording may only appear when
the state is `evidenced_independent`.

`unknown_not_proven` does not block ingestion or backtest
research, but T034 must surface the limitation in every report.
The state may only be changed to `evidenced_independent` after
separate auditable operational or infrastructure evidence has
been obtained; until then, the state remains `unknown_not_proven`
or `known_correlated`.

### Recorded known-common operator / upstream infrastructure

The report records any known common operator, upstream data
source, shared deployment, shared caching layer, shared failure
domain, or other shared infrastructure between the two endpoints,
even when that sharing is partial or suspected. This field is
the input that supports the infrastructure-correlation evidence
state above.

## Acceptance

- **seeded defect fixtures trigger the correct reason code** —
  every defect listed below has a fixture whose expected reason
  code is named in the contract, and the report must surface that
  reason code when the fixture is replayed:
  - range-coverage gap → `range_coverage_gap`;
  - block / hash gap → `block_hash_gap`;
  - duplicate `EventKey` → `duplicate_event_key`;
  - misordered log → `misordered_log`;
  - unknown pool → `unknown_pool`;
  - decode error → `decode_error`;
  - impossible value → `impossible_value`;
  - stale endpoint → `stale_endpoint`;
  - metadata failure (chain ID / genesis / block hash / code
    hash) → `metadata_failure`;
  - cross-provider discrepancy (same `EventKey`, different
    content) → `cross_provider_discrepancy`;
  - budget exhaustion → `budget_exhausted`;
  - capability regression → `capability_regression`;
  - `User-Agent` 403 → `user_agent_rejected`;
  - required A+B sample missing → `cross_endpoint_sample_missing`;
  - required A+B sample disagreeing →
    `cross_endpoint_sample_disagree`;
  - infrastructure-correlation state unrecorded →
    `infrastructure_correlation_state_unrecorded`;
  - qualified-checkpoint mismatch → `checkpoint_mismatch`;
- **`complete=true` requires, all of:**
  - **zero unexplained gaps / errors** — every gap, error, and
    capability regression is named with a reason code and is
    either resolved or explicitly recorded as a known
    limitation that downstream consumers can read;
  - **no exhausted budget** — no `budget_exhausted` reason
    code is raised;
  - **successful required A+B samples** — every required
    sample from Decision 6 has been executed and the two
    endpoints agreed on every comparison; the selection
    inputs are recorded so the selection can be reproduced;
  - **dataset manifest checksum recorded** — the SHA-256 of
    the dataset manifest is present in the report and is
    reproducible from the durable manifest store;
- **empty selective capability probes count for range acceptance
  only, never for event completeness** — an all-empty
  capability probe proves the endpoint accepted the request
  range but does not prove the dataset is event-complete; a
  result-bearing required sample is still required when the
  dataset contains any events;
- **cold-start coverage begins at the selected pool's
  registered Initialize event** — for a cold start (no
  previously qualified local checkpoint), the report names the
  pool's on-chain `Initialize` block and verifies coverage
  from that block to the requested end block. A cold-start
  dataset that does not reach the pool's actual Initialize
  block is incomplete;
- **warm run verifies the qualified checkpoint and the complete
  suffix** — for a warm run (a previously qualified local
  checkpoint exists), the report names and verifies the
  qualified checkpoint (chain, contract, last successful
  block, schema/decode version, manifest checksum) and the
  complete suffix after it. A warm run whose checkpoint does
  not match the requested pool and range is rejected;
- **backtest-window-only download is incomplete without
  Initialize or qualified checkpoint** — a backtest-window-only
  download whose scan begins after the pool's Initialize
  block and that has no qualified local checkpoint is recorded
  as incomplete even when every requested window block was
  scanned;
- **required A+B sample selection is reproducible** — given the
  PoolId, partition bounds, EventKey, and manifest of a
  qualified dataset, the required sample selection is
  reproducible from these inputs alone; the report does not
  rely on random number sources or wall clock for sample
  selection;
- **warning counts do not disappear in aggregates** — every
  deviation, retry, `User-Agent` rejection, capability
  regression, and budget overrun is a distinct row in the
  deviation ledger; the aggregate counters are derived from
  those rows, never from a separate counter that could
  silently swallow a warning;
- **infrastructure-correlation state is surfaced in every
  report** — the enum value is never blank, the
  `cross_endpoint_agreement` wording is used, and the explicit
  residual-risk callout is present whenever the state is
  `unknown_not_proven` or `known_correlated`.

## Must not

- let warning counts disappear in aggregates. Every deviation is
  a distinct row in the deviation ledger;
- treat a third-party match (a dashboard, an explorer, a
  subgraph, a third-party index) as proof of dataset correctness
  when raw chain evidence is incomplete. The qualification
  evidence is the dataset's own raw evidence plus the A+B
  comparison, not any external source;
- claim `independent_provider_agreement`. The report uses
  `cross_endpoint_agreement` unless the
  infrastructure-correlation state is `evidenced_independent`;
- leave the infrastructure-correlation state blank. The state is
  one of `unknown_not_proven`, `known_correlated`, or
  `evidenced_independent`, and the current value is
  `unknown_not_proven`;
- change the infrastructure-correlation state to
  `evidenced_independent` without separate auditable
  operational or infrastructure evidence. Until then the state
  remains `unknown_not_proven` or `known_correlated`;
- use random number generation or wall clock for required A+B
  sample selection. Sample selection depends only on PoolId,
  partition bounds, EventKey, and manifest — deterministic
  inputs only;
- relax any Acceptance clause above in order to make a partial
  implementation pass. A failing acceptance clause is a contract
  gap, not a test bug.
