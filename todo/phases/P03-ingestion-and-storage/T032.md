# T032 — Implement checkpointed historical ingestion

> Phase: `P03`

## Dependencies

T020, T022, T031

## Outcome

T032 implements **capability-driven historical ingestion** for a single
selected PoolKey, with **A+B routing** per ADR-010 and ADR-011. Bounded
scans resume without gaps or duplicate canonical events. The run is
split into two physical modes:

- **Cold-start history** — the first time the requested pool is
  ingested, or whenever no previously qualified local checkpoint
  exists. The scan starts at the selected pool's registered `Initialize`
  block (the on-chain block at which that `PoolKey` was first created
  on Robinhood Chain mainnet) and proceeds contiguously to the requested
  end block. A shorter backtest start does **not** truncate the
  reconstruction prefix: reconstruction must reach the pool's actual
  initialization in order to rebuild the tick bitmap, the
  liquidity-net crossings, the active-liquidity series, and the
  protocol-fee history without relying on future-state assumptions.
- **Warm incremental ingestion** — when a previously qualified local
  checkpoint exists for the same pool, the scan is restricted to the
  missing suffix after that checkpoint and never re-ingests an already
  qualified prefix.

Capability, routing, and budget are decided from a preflight probe
recorded in the run manifest, not from any assumed provider plan.
Provenance is recorded per successful or failed interval. Provider
failover does not silently merge two partial responses into one
supposedly complete range.

A run is **complete** only when every requested block in the scan
range is covered exactly once by either a successful interval or an
explicitly recorded empty interval. Failed, cancelled, and skipped
intervals remain uncovered; the checkpoint cannot advance past them
and `complete` remains `false`. The "local-skip-then-complete" path is
forbidden: there is no execution shape in which the qualification
state is `complete=true` while any interval in the requested range is
uncovered.

## Deliverables

### Range planner and run topology

- a **range planner** that, for a given pool, requested end block, and
  requested start block, builds the scan topology for the run:
  - cold-start topology — one bounded sub-range starting at the
    pool's `Initialize` block and ending at the requested end block;
  - warm topology — suffix-only sub-ranges after the qualified local
    checkpoint, plus a prefix-leave-alone boundary that is verified
    against the checkpoint before any block after it is ingested;
  - the planner refuses to start a warm run when the existing
    checkpoint's manifest, block hash, schema/decode version, or
    coverage prefix does not match the requested pool and range;
- the planner chooses the **scan filter** as one pool-filtered topic0
  OR query covering `Initialize`, `ModifyLiquidity`, `Swap`, and
  `Donate`, plus the inherited `ProtocolFeeUpdated` event from the
  same pinned v4-core ABI artifact used by T021, with topic1 fixed to
  the selected `PoolKey`'s `poolId`. The system must not multiply a
  scan into one request stream per event type when one bounded OR
  filter suffices.

### Preflight probe and capability/budget ledger

- a **preflight probe** that runs at the start of each ingestion run
  and records, per endpoint:
  - alias, chain/deployment identity, supported finality tags,
    archive-state depth, accepted log range, latency, and probe
    block/hash;
  - measured capability for `eth_getLogs` (max blocks per request,
    observed response size, observed rate-limit headers), and
    measured capability for block-header reads;
  - the **call / compute-unit / time budget** allocated to this run,
    broken down per endpoint;
  - the **remaining-budget bound** for this run, sourced from either
    operator injection at run start or from a provider usage API
    consulted before the scan begins. The remaining-budget bound is
    recorded in the manifest before any RPC traffic is sent. The run
    does **not** assume an unused monthly quota; an unspecified or
    unobservable remaining budget is recorded as
    `remaining_budget_source = operator_injection_unknown` or
    `remaining_budget_source = provider_usage_api_unavailable` and
    is treated as a hard cap of zero;
- preflight probe results persist to durable storage (the SQLite
  manifest store from T031) before the scan starts, so a crash at any
  later boundary still leaves the recorded capability and budget for
  replay and for the next run's planning.

### Provider routing and failover

- the **initial wide-range log source** is the Robinhood public RPC
  endpoint, used for `eth_getLogs` over broad sub-ranges, with
  adaptive split on range, response-size, timeout, throttling, or
  single-block overflow errors. Every Robinhood request carries an
  explicit non-secret application `User-Agent` whose value comes from
  configuration; missing or default `User-Agent` values that cause an
  HTTP 403 (for example urllib's default `User-Agent` against the
  Robinhood public endpoint) are surfaced as a hard 403 retry with
  the configured application `User-Agent`, and as a persistent
  capability failure when the configured `User-Agent` itself is
  rejected;
- **Alchemy Free** supplies archive and block-pinned reads and
  sampled verification, including the pool's `Initialize` block
  discovery through archive state when the Robinhood public RPC's
  pruned history cannot resolve it. Alchemy Free may take over log
  intervals only through its measured plan (observed and documented
  to be on the order of 10 blocks per `eth_getLogs`) and within its
  measured call / CU / time budget;
- **failover** is allowed only within an endpoint's measured
  capability and remaining budget. The routing policy per interval
  is:
  - if A fails, B may take the interval only if B's measured
    capability covers the interval **and** B has sufficient
    remaining budget. When B succeeds within those bounds and
    completes a durable commit, the interval is recorded as
    successful under B;
  - if A and B both fail, if no endpoint has the measured capability
    to take the interval, or if the remaining budget is exhausted
    before the interval can be covered, the interval is recorded as
    **failed / uncovered** and the qualification halt is triggered;
  - the routing decision per interval, including the failover path
    used, is persisted in the run manifest so the evidence trail
    explains why each interval was assigned where it was;
  - **checkpoint cannot advance past any failed / uncovered
    interval.** Subsequent intervals that happen to be temporarily
    captured (for example a future suffix fetched ahead of the gap
    by a concurrent attempt) may be persisted as **provisional
    data** but must not be promoted into the contiguous checkpoint
    and must not be used to set `complete=true`.

### Scanned-empty / failed / cancelled boundary

The three coverage states are mutually exclusive and enforced by the
range planner and the storage layer. They are persisted with
explicit reason codes so the manifest can distinguish them.

- **scanned_empty** — the `eth_getLogs` request succeeded, the
  response was valid, the response decoded as a JSON-RPC success
  with a non-null `result` whose logs array is empty, and the
  interval plus a fixed-block-pinned reference (the block hash of
  the head of the interval, captured at probe or scan time) is saved
  alongside the empty result as durable evidence. A scanned-empty
  interval counts as covered for qualification;
- **failed** — any of: an RPC / HTTP error, an RPC timeout, an HTTP
  403 or 429, a budget-exhaustion reason code raised by the routing
  policy, a response that is invalid or not cross-checkable, or any
  other irreducible provider error. A failed interval is **not**
  covered; the checkpoint cannot advance past it; `complete` is
  `false`;
- **cancelled / skipped** — an interval that the planner or the
  operator marked as cancelled, or that the planner decided to skip
  for reasons other than a successful empty response. Cancelled and
  skipped intervals remain **uncovered** and are never recorded as
  empty. They produce an explicit reason code distinct from
  `scanned_empty` and from `failed`, but they share the same
  qualification consequence: the checkpoint cannot advance past them
  and `complete` is `false`.

Budget exhaustion is recorded with the explicit reason code
`budget_exhausted` (and a sub-tag identifying which budget: calls,
CU, time, or provider-side response quota). `budget_exhausted` is
**failed**, never `scanned_empty`. There is no execution shape in
which a partial run whose budget ran out is marked `complete=true`.

### Durable checkpoint, retry ledger, run manifest

- a **durable checkpoint** whose contents are atomically committed
  per ADR-002 / T031 — never partially updated — and that records,
  per pool: the qualified block range (start, end), the last
  successful block per endpoint, the schema/decode version, the
  capability snapshot that produced the checkpoint, and a
  referenceable coverage prefix. The checkpoint only advances after a
  durable commit of the corresponding interval and a recorded
  coverage transition from uncovered to covered;
- a **retry ledger** that records every retry attempt with its
  endpoint, the interval it tried to cover, the reason for retry
  (timeout, 403, 429, response-size overflow, single-block
  overflow, rate-limit, capability downgrade, budget tick, etc.),
  and its outcome. The retry ledger is append-only and is checksummed
  alongside the manifest;
- a **run manifest** that records, per run:
  - logical RPC calls (one logical RPC call per `eth_getLogs`
    request; HTTP batches, when added by the transport, do **not**
    reduce the logical RPC call count),
  - HTTP requests / batches,
  - response bytes,
  - normalized rows,
  - provider units when the provider reports them (for example
    Alchemy CU),
  - elapsed time,
  - deviations from the preflight plan (capability regression,
    budget overrun, observed limit lower than measured, observed
    10-block cap on Alchemy, Robinhood User-Agent 403, response-size
    overflow, rate-limit retry, provider failover, etc.);
- the manifest's recorded interval table distinguishes
  `scanned_empty`, `successful`, `failed`, and `cancelled / skipped`
  rows with their reason codes, and the failure path for each
  failed row is reproducible from the manifest alone.

### Deterministic normalization pipeline

- a **deterministic normalization pipeline** that reuses T030's
  schema and decode surface and T031's storage writer, with no
  re-implementation of the logical schema or the physical layout:
  - raw JSON-RPC response bytes, topics, data blob, and response
    wrapper survive intact through canonical serialization;
  - the typed event body is produced from the same pinned ABI
    artifact used by T030 / T021;
  - the normalized event identity follows T011 `EventKey`
    `(chain_id, block_hash, tx_hash, log_index)`;
  - the normalized content hash follows T030's rule
    (typed body + `EventKey`, observational fields excluded);
  - acquisition provenance (endpoint alias, retrieval time,
    request interval, HTTP batch metadata) lives in the raw
    envelope / manifest, is observational, and is not part of the
    normalized content hash.

### Block header policy

- for every distinct event block discovered in the scan range, the
  pipeline fetches **one non-hydrated block header** (block hash,
  parent hash, integer timestamp, and the minimum block metadata
  required for ordering) and reuses that header across every event
  that lands in that block;
- the pipeline does **not** download hydrated blocks, all
  transactions for a block, or all receipts for a block as part of
  ordinary pool-history ingestion. A receipt is fetched only when a
  later hook-evidence or reconciliation task explicitly requires it.

## Acceptance

- **kill / restart at each boundary** — killing and restarting the
  run at every durable-commit boundary, including mid-interval
  after a successful RPC but before commit, mid-retry-ledger
  append, mid-manifest row, and mid-block-header write, leaves the
  persisted state equal to either the previous committed state or
  the complete new state. No run state is left half-written;
- **overlapping and concurrent-run tests converge** — running two
  ingestion workers against overlapping ranges of the same pool
  either elects one as the writer and lets the other observe the
  same coverage, or coordinates via the durable checkpoint so the
  final state is indistinguishable from a single successful run.
  Concurrent attempts must not produce duplicate canonical events,
  must not regress a qualified prefix, and must not promote a
  provisional interval past an uncovered one;
- **every requested block is covered exactly once** — for the
  requested scan range, the manifest's interval table accounts
  for every block exactly once, by either a successful interval or
  an explicit `scanned_empty` interval pinned to a saved
  fixed-block reference. No block is double-counted. No block is
  silently dropped;
- **failed intervals prevent completion** — when any interval is
  in state `failed` or `cancelled / skipped`, the checkpoint does
  not advance past it and `complete` is `false`. A run whose
  budget exhausted before the last interval was covered is
  recorded with reason code `budget_exhausted` and `complete=false`,
  never as a complete run;
- **fixtures cover, at minimum:**
  - Alchemy's observed and documented ~10-block `eth_getLogs` cap,
    exercised both as a measured capability and as a hard cap when
    the preflight budget does not allow a retry;
  - Robinhood wide-range success followed by an adaptive split
    triggered by range, response-size, timeout, throttling, or
    single-block overflow;
  - HTTP 403 caused by a missing or blocked `User-Agent`, with
    the configured non-secret application `User-Agent` retry path
    and the persistent failure path when the configured
    `User-Agent` itself is rejected;
  - response-size overflow that triggers an adaptive split rather
    than dropping the interval;
  - rate limiting (HTTP 429) handled by classified retry without
    advancing the checkpoint;
  - budget exhaustion producing reason code `budget_exhausted`
    and `complete=false`, with no path that reclassifies a
    budget-exhausted interval as empty;
  - provider failover from A to B within B's measured capability
    and remaining budget, with the failover path persisted in the
    manifest and no gap in coverage;
- **run manifest records, per run**: logical RPC calls, HTTP
  requests, response bytes, normalized rows, provider units when
  reported, elapsed time, and every deviation from the preflight
  plan (capability regression, lower-than-measured observed cap,
  budget overrun, retry bursts, failover events, 403 / 429
  responses, response-size overflow, single-block overflow, etc.);
- **tests distinguish cold-start history from warm incremental
  ingestion** — there is at least one cold-start fixture that
  scans from the pool's `Initialize` block to the requested end
  block, and at least one warm fixture that begins from a
  previously qualified local checkpoint and ingests only the
  missing suffix;
- **checkpoint rejection on mismatch** — the system rejects
  (refuses to advance, refuses to set `complete=true`) any
  checkpoint whose manifest, block hash, schema/decode version,
  or coverage prefix does not match the requested pool and range.
  Rejection is exercised by a dedicated test that mutates one of
  those fields and asserts the rejection.

## Must not

- advance a checkpoint before a durable commit of the corresponding
  interval has been recorded in the manifest store;
- infer empty coverage from an empty table, an empty response that
  cannot be cross-checked, or any other non-positive evidence.
  `scanned_empty` requires a successful RPC, a valid response, and
  a pinned block reference;
- continue past an irreducible failed block and call the run
  "complete". A failed interval halts qualification;
- issue one `eth_getLogs` scan per event type when a single topic0
  OR filter combined with a topic1 `poolId` filter suffices;
- describe HTTP batches as fewer logical RPC calls. A JSON-RPC
  batch counts as one HTTP request and as the number of logical
  RPC calls it carries, never as fewer;
- download hydrated blocks, all transactions for a block, or all
  receipts for a block as part of ordinary pool-history ingestion;
- record a credential-bearing URL (any URL whose authority contains
  userinfo, or whose query string carries a secret-like key) into
  raw, normalized, manifest, or provenance storage. URLs are
  reduced to endpoint aliases sourced from configuration;
- assume a fixed provider-side block cap (for example a
  10,000-block cap) as a planning constant. Capability and budget
  are measured per run from the preflight probe, not assumed from
  a published plan;
- silently reclassify an interval that was cancelled or skipped as
  empty. Cancelled / skipped intervals are uncovered and remain
  uncovered;
- advance a contiguous checkpoint or set `complete=true` while any
  interval in the requested scan range is uncovered, regardless of
  how many subsequent intervals were provisionally captured.
  Provisional future-suffix data must not be promoted across a
  failed / uncovered gap;
- mark a run whose budget exhausted before the last interval was
  covered as complete. Budget exhaustion produces reason code
  `budget_exhausted` and forces `complete=false`;
- claim a provider failover that crosses outside the failing
  endpoint's measured capability or remaining budget as a
  successful coverage transition. The interval must be recorded
  as `failed` instead.

- **Decision 4 (T032 specific) — provider failover, scanned-empty,
  failed, and cancelled / skipped boundary** — A failover to B is
  allowed only within B's measured capability and remaining budget;
  A and B both failing, no capable endpoint, or budget exhaustion
  marks the interval as `failed` and halts qualification. The
  checkpoint cannot advance past a failed / uncovered interval.
  Subsequent provisional suffix data must not be promoted into a
  contiguous checkpoint and must not set `complete=true`. The
  three coverage states are strictly distinguished:
  `scanned_empty` (RPC success, valid response, empty array, with
  the interval and a pinned block reference saved as durable
  evidence), `failed` (RPC / HTTP error, timeout, 403, 429,
  `budget_exhausted`, invalid response, or uncross-checkable),
  and `cancelled / skipped` (still uncovered, never logged as
  empty). Budget exhaustion produces the explicit reason code
  `budget_exhausted` and `complete=false`. There is no path that
  "skips locally then stays complete". The preflight probe must
  retain a remaining-budget bound sourced from operator injection
  or the provider usage API; unused monthly quota is never
  assumed.
