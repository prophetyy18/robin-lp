# T037 — Close the silent partition row-loss defect

> Phase: `P03`
> Contract status: `OWNER_PLAN_EXTENSION_2026-09-18`

## Dependencies

T031, T036

## Outcome

a partition write that would leave the on-disk Parquet file missing EventKeys
already recorded in `event_index` fails closed instead of reporting success, so
no dataset can be reported `complete=true` while its Parquet files and its event
index disagree.

Reproduced defect: the 2026-09-18 reference run
(`run-680e65f4a59842d98b1712a45280779d`) recorded 3,739 rows in `event_index` but
wrote 3,737 rows to Parquet. The two missing rows are Swap events at block
`55586273` (log index 53, tx `0x17c7771d139bbf8f8cb7d5b7b1cd0ccb09ca6aefa43b6e36df400e26fb5e936e`)
and block `55726297` (log index 29, tx `0xd75437f4a29d3763edf90eebc8cfd179f63b2f278f01d9b9663ac2ab0a5d79d4`).
Nothing recorded the loss: `reorg_journal`, `conflicting_observations` and
`run_manifest_deviations` are all empty and the run reported `complete=1`.

Root cause (verified by reading the code, not inferred): the runner groups
decoded rows by `(event_name, block_number // 100 * 100)` and writes each group
as one `writer.append_partition` call (`src/robinhood_lp/ingestion/runner.py:887-929`).
When the partition cell already exists, `RawPartitionWriter._merge_into_existing_partition`
appends only to `event_index` and deliberately does not modify the Parquet file
(`src/robinhood_lp/storage/writer.py:557-585`). Collection intervals are 10,000
blocks wide and start at an offset of 37 inside a 100-block cell, so every
interval except the first writes new forward-progress rows into a cell the
previous interval already created; those rows reach the index but never the file.

The same density that produced two losses in one million blocks extrapolates to
roughly twenty to thirty-five lost rows per pool over a ten-million-block window,
so this task closes the defect before the wider acquisition depends on it.

## Deliverables

1. A fail-closed guard in the partition write path: when an incoming batch
   contains EventKeys that the existing on-disk Parquet file does not contain,
   the write either stores those rows or fails with a reason code. Silently
   appending index rows without storing the corresponding Parquet rows is not an
   available outcome.
2. Removal of the condition that creates the situation: forward-progress
   collection must not land new rows in an already-written partition cell, either
   by aligning collection interval boundaries to the partition grid or by an
   equivalent mechanism that preserves append-only semantics.
3. A per-partition reconciliation check comparing the `event_index` EventKey set
   and row count against the Parquet file, surfaced through the data-quality
   report so `complete=true` cannot be produced while any partition disagrees.
4. A regression test that reproduces the original conditions from a fixture: one
   collection interval writing new blocks into a partition cell created by an
   earlier interval. The test asserts the rows are stored, or that the write
   fails closed; it must not assert the silent-append behaviour.
5. A written record of the defect, the root cause above, and which of the two
   remedies was applied, in the task evidence.

## Acceptance

- the regression fixture that previously lost rows now either stores every row or
  fails closed with a documented reason code, and a test asserts that the
  index-only outcome is impossible;
- reconciliation reports a mismatch for a deliberately inconsistent partition
  fixture and passes for a consistent one, with the mismatch naming the partition
  and the missing EventKeys;
- re-checking `/home/lpdev/lp-data` (the 2026-09-18 run) through the new
  reconciliation path reports its two missing Swap rows rather than `complete=true`,
  and this observation is recorded as evidence; no repair of that dataset is
  attempted by this task;
- a genuine re-run of an already-covered block range remains idempotent: no
  duplicated rows, no mutated Parquet bytes, and the existing idempotency tests
  still pass unchanged;
- `pytest`, Ruff format/check and the strict type checker pass.

## Must not

- rewrite, truncate, delete or mutate already-committed Parquet bytes, or abandon
  append-only semantics; a repair path that edits a written partition file is out
  of scope;
- weaken the existing re-run / overlap behaviour that T031 specifies, or relax an
  existing test, tolerance or type to make the change pass;
- delete, patch or re-qualify the 2026-09-18 reference dataset, or edit any T030,
  T031, T032, T033, T034, T035 or T036 contract text;
- infer the defect from the writer alone: reproduce it through the runner path
  before changing either file;
- change the meaning of `complete` for any other task.
