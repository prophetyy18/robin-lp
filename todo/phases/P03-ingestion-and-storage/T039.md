# T039 — Acquire the per-pool extended-history research window

> Phase: `P03`
> Contract status: `OWNER_PLAN_EXTENSION_2026-09-18`

## Dependencies

T035, T036, T038

## Outcome

Each pool in the research universe is acquired from its own `Initialize` block, or
the earliest block at which it existed, up to one agreed finalized block, so the
research dataset covers the pool's observable life instead of a fixed-width slice.

The ten-million-block rule implemented by the superseded T038 is replaced by a
per-pool window. T038's module, tests and dataset generations remain immutable
historical evidence: they are not edited, re-qualified or merged, and no clause of
this task may cite the ten-million-block window as the research range.

**One acquisition run covers exactly one `PoolKey`.** The research universe is built
by running the acquisition once per pool, never by widening a single run to several
pools or chains. This is what keeps the task compatible with the ingestion contract
it extends, whose prohibition on widening still stands unchanged.

This task produces the dataset generation that the research dataset registry
consumes. It reuses the acquisition shape already fixed by the ingestion ADRs
rather than defining a second one: one pool-filtered range query per planned
sub-range, events persisted with their `(block_number, transaction_index,
log_index)` position, state rebuilt locally downstream, and no `eth_call` during
acquisition.

Measured context, re-probed every run and never assumed: the observed block
interval is about 0.1008 seconds (derived from this project's own persisted block
headers), so a ten-million-block window is about 11.7 days while the full chain
history is about 76 days. Widening the window is the difference between a research
dataset that can support a model and one that cannot.

## Deliverables

- A window planner that computes, per pool, an inclusive start at that pool's
  `Initialize` block and an inclusive end at the run's agreed finalized block, and
  records both with the evidence that produced them.
- The finalized end read from both qualified endpoints at run start; the two
  readings must agree on block number **and** block hash, and the agreed block is
  pinned by number and hash into the run record, the per-pool coverage report and
  the evidence pack.
- A per-pool data root and a per-pool coverage report, so one pool's agreement is
  never presented as another pool's result.
- Log-query splitting that respects the measured per-call log ceiling, and header
  retrieval deduplicated per distinct event block and issued as JSON-RPC batches.
- A cost record per pool separating logical calls, HTTP requests, bytes, rows,
  provider units and elapsed time, with a declared budget ceiling that halts the
  run rather than being exceeded silently.
- An operator runbook entry naming the endpoint able to serve historical state at
  the required depth, since that capability differs between the qualified
  endpoints.

## Acceptance

Two materially different pools are acquired over different-length windows, each
carrying its own data root and its own coverage report; a pool whose `Initialize`
cannot be located in its candidate window stops with a named reason and is reported,
never silently included, excluded or covered by another pool's window; `latest`, a
non-finalized block and any wall-clock-derived bound are rejected as the window end,
including as a fallback when the finalized tag is unavailable; a finalized
disagreement between the two qualified endpoints halts the run; interrupting and
resuming a window is indistinguishable from an uninterrupted acquisition; re-running
a completed window issues no new chain reads for the covered range and reproduces
byte-equivalent canonical output after excluding declared observational fields; the
per-pool reports reconcile against the acquired partitions; and the superseded
reference generations are neither read as input nor modified.

Boundary and failure cases covered: a pool initialized at the earliest block the
chain can serve; a pool initialized after the agreed end; two pools whose windows
overlap partially, fully and not at all; an endpoint that cannot serve historical
state at the required depth; budget exhaustion mid-window; and a provider returning
a non-finalized block for the finalized tag.

## Must not

Invent a chain read the ingestion ADRs forbid, such as one `eth_getLogs` call per
block, one header fetch per scanned block, or any `eth_call` during acquisition;
fall back to `latest` or to a wall-clock-derived bound; interpolate, forward-fill or
synthesize a gap; widen one pool's window to reach another pool's `Initialize`;
cover more than one `PoolKey` in a single acquisition run, or merge two pools into one
dataset or one coverage report; edit, re-qualify, overwrite
or merge the superseded reference generations; redefine the acquisition shape; or
treat a lower observed cost as evidence that a wider window is complete.
