# T008 — Add the on-demand global progress view over the plan

> Phase: `P00`
> Contract status: `OWNER_PLAN_EXTENSION_2026-09-19`

## Dependencies

None.

## Outcome

anyone can ask this repository what the plan is doing and get a plain-language answer about every
phase and task — what each is for, where it stands, what is approved and still live, what is
blocked or has changes requested, and what is ready next — without reading `todo/config.yaml` and
without a stored report that the next commit turns into a lie.

## Deliverables

1. An on-demand renderer, a command run as `python -m tools.progress` whose code lives under
   `tools/` outside `tools/workflow/`, that reads the committed `todo/config.yaml`, the phase
   READMEs under `todo/phases/` and the task contracts they point at, and prints:
   - every phase, what it is for (from that phase's own README) and its tasks;
   - every task, in plain language: its identifier, its title and what it is for (from its own
     contract, not restated in the renderer), its phase and its status;
   - the approved set split into what is still live and what is superseded, with the successor
     named for a retired task;
   - every task whose state is blocked, changes-requested, triage-required or awaiting an owner
     decision, named as such;
   - the ready-next set: every `PLANNED` task whose dependencies are all `APPROVED` and none of
     which is superseded — the dependency condition `ready` checks, reported for the whole plan
     rather than for one task, so the reader sees every candidate the Manager may choose from.
2. The view is generated on demand and never committed: the command writes nothing but its
   standard output and its exit status, no rendered plan file, digest, cache or snapshot is added
   to the repository, and running it leaves the working tree unchanged.
3. The view records no fact that the next commit falsifies: no commit SHA, no test count, no
   pass/fail tally, no wall-clock time, and no stored copy of a status. Every fact it prints is
   read from the committed configuration at run time, so a status change moves the view with it.
4. It fails closed instead of printing a view it cannot substantiate. A configuration it cannot
   read or parse, a status outside the plan's state machine, a dependency or supersession pointer
   that does not resolve, and a configured task whose contract file is missing each produce a
   non-zero exit and a plain-language message naming the problem; a check mode (a documented flag,
   for example `--check`) performs exactly these checks and exits non-zero on the first one it
   finds and zero on a plan that renders faithfully.
5. Committed tests: one that runs the renderer against the committed `todo/config.yaml` and
   asserts the rendered view covers every configured phase and task exactly once with its status
   and the ready-next set, and one that proves the check can fail, on the fixture inputs of
   deliverable 4, so a check that never fires cannot pass as a check that passes.

## Acceptance

the command runs from a clean checkout with no third-party dependency and no network access, and
its plain-language output contains each phase and each task of the committed configuration exactly
once; the approved set is separated into live and superseded tasks and each retired task names its
successor; blocked, changes-requested, triage-required and owner-decision tasks are each named as
such; the ready-next set is exactly the `PLANNED` tasks whose dependencies are all `APPROVED` and
none of which is superseded — the dependency condition `ready` checks — computed from the
configuration alone; the output contains no commit-SHA-shaped token, no test or pass count and no
timestamp, and a fixture configuration with a changed status, a changed dependency or a superseded
dependency produces a correspondingly different view, proving nothing is baked into the renderer;
running the command leaves the repository without a new or modified file; the check mode exits
non-zero for each declared failure input and zero for the committed plan; `pytest`, `ruff check`,
`ruff format --check` and `mypy src tests` pass, and `mypy` is unaffected because the renderer is
outside `src/`.

## Must not

live under `tools/workflow/`, which no role and no amendment layer may change, or add a module
under `src/robinhood_lp/`, where every module needs a layer from the layer map and a plan tool is
not product code; write, commit or cache a rendered report; print a commit SHA, a test count, a
timestamp or any status that is not read from the configuration at run time; infer readiness from
anything other than the plan's own fields, or decide a task's state; duplicate the repository
checks that T005 and T006 own — this task renders the plan, it does not re-validate citations or
layer imports; add a third-party dependency or a network read; edit `todo/config.yaml`, a task
contract, `todo/schemas/`, `.claude/`, `tools/workflow/`, `src/` or `docs/` — the renderer reads
the plan and never rewrites it; weaken an existing CI job, test or assertion.
