# T112 — Repair the T109 product-run evidence pipeline to use real T100 partitions and preserve fill-cursor run facts

> Phase: `P06`
> Contract status: `OWNER_AMENDMENT_A0026`

## Dependencies

T040, T041, T052, T061, T100, T104, T109

## Outcome

The product backtest entry enters T061 from real T100 partitions through the existing
replay and features paths, never from a fixed empty event source. Every new manifest
references real and resolvable-to-same-canonical-bytes T100 partition references; no
reference is invented from an event cursor or a coverage string. Every new simulation
evidence artifact preserves enough run-specific facts at the actual fill cursor to
restore position, integer inventory, equity, drawdown and T052 attribution, and never
conflates `block_range` with `tick_range`. Approved T069, T105 and T109 evidence,
artifacts, status, attempts, commit identities and review records stay byte-identical.

## Deliverables

Re-route the current T109 product backtest entry so that it loads the dataset's
immutable T100 partitions and resolves them through the existing T040/T041 replay
and T049 features paths. The fixed empty event source used by the approved T109
implementation is no longer reachable as a current authoritative entry.

For each new successful run, the manifest's `dataset_partition_refs` resolves to the
same canonical bytes T100 registered, with the same content hash, range and PoolKey.
A reference cannot be authored from an event cursor, a coverage string, a placeholder
or a synthetic list; the loader rejects mismatched or non-resolvable references with
a named reason.

For each new simulation evidence artifact, the manifest records `block_range` and
`tick_range` as separate fields whose bounds agree with the partition's source range
and the dataset's registered reconstruction but cannot cross-write one into the other.
The artifact carries enough run-specific facts —position snapshot, raw token amounts,
integer `liquidity`, realized fees, cost components, equity, drawdown and T052
attribution components —bound to the actual fill cursor so a `RunState` reader at
that cursor restores them through the existing T061 engine and T052 attribution
semantics, never through a strategy callback, a range-derived synthetic, or an
interpolated tick.

Every existing T109 obligation carries forward through T112: causal cursor binding at
emission, strictly increasing `run_transition_ordinal`, atomic publication of manifest,
report and simulation evidence, dataset-referenced manifest without an embedded market
event copy, sparse checkpoint plus deterministic transitions, read-time `ReplayFrame`
composition, no strategy rerun, byte-identical legacy records readable only through
the versioned legacy reader, and no replacement replay, backtest, accounting, fee or
publication authority.

`T112` declares `replaces: [T109]`. Until `superseded_by` records retirement, T109
remains the only current authority and every PLANNED direct consumer continues to
depend on T109; once every PLANNED direct consumer is repointed, a SUPERSEDE
amendment annotates T109 `superseded_by T112` and T112 becomes the sole current
authority for new writes.

## Replacement and migration

- **Old code reachability:** the new product backtest entry becomes the only current
  entry path and the fixed empty event source path becomes non-current for new runs.
  No new module, replay path, accounting engine, fee projection, publication authority
  or risk/execution/signer surface is created; the existing T040/T041 replay, T061
  engine and accounting, T052 attribution, T069 orchestrator entry point and T105/T109
  reports publishers are adapted through T112.
- **Historical data and artifacts:** every T069, T105 and T109 manifest, report,
  simulation evidence, candidate lock, search manifest, robustness report, review
  artifact, approval commit, evidence pointer and review record stays byte-identical
  and read-only. A pre-T112 T109 result is never regenerated, reconciled, reinterpreted
  or backfilled under T112; the versioned legacy reader remains its only current path.
- **Runtime cutover and rollback/fail closed:** T112 becomes current atomically with
  its first approved successful publication. If any binding —real-partition
  resolution, block_range vs tick_range separation, fill-cursor preservation—
  cannot be written and validated, publication fails closed. Rollback reverts to the
  last T109-compatible release or disables new successful publication; it never
  serves a T112 result through the T109 publication path or a T109 result through
  the T112 publication path.
- **Downstream dependencies:** T073, T084, T085, T086, T087, T088, T103, T107, T108,
  T110 and T111 continue to consume T109 evidence and provenance through their
  current contracts while T109 remains APPROVED. Future CONTRACT amendments must
  replace T109 with T112 in each PLANNED direct consumer and add the corresponding
  replacement dependency. T107 must bind its candidate lock and T108 must teach the
  authoring guide to T112 evidence and provenance. T096 must carry T112's
  independently reviewed pipeline-repair evidence into the final V1 matrix alongside
  T109's evidence. T110 and T111 must compose T112 evidence through the same T040 /
  T041 / T104 reconstruction and T052 attribution already required; they must not
  duplicate T112's pipeline. Until repointing completes, `T112` stays `PLANNED` and
  is unavailable to the dependency graph.
- **Security:** T112 evidence confers no strategy registration, no risk approval, no
  paper/live permission, no execution authority and no signer activation. Manifests,
  reports and simulation evidence contain no private key, signing payload, endpoint
  secret, webhook credential, `.env` value, RPC URL or authorization header.
  Tampering, substitution, downgrade to the fixed empty event source, downgrade to
  a cursor-fabricated or coverage-fabricated partition reference, and downgrade to
  block_range-conflated tick_range all fail closed with named reason codes.
- **Verification:** the existing T109 verification matrix — two heterogeneous pool
  fixtures, beginning / intra-block / end-of-block / range-end cursor queries,
  immediate and delayed fill cursor binding, three-event A-B-C delayed-fill cursor
  monotonicity, sparse-checkpoint equivalence, strategy-replacement byte equivalence,
  T052 attribution equivalence, legacy T069/T105/T063 unavailable behavior,
  predecessor publisher unreachable, atomic publication and shared canonical
  timeline tests—remains passing and must additionally prove the three pipeline
  invariants: (a) the product backtest entry resolves to real T100 partitions and
  refuses the fixed empty event source; (b) every accepted manifest
  `dataset_partition_refs` resolves to the same canonical bytes T100 registered,
  with mismatched, cursor-fabricated or coverage-fabricated references rejected by
  named reason; (c) every accepted simulation evidence artifact carries
  `block_range` and `tick_range` as separate fields and preserves enough fill-cursor
  run facts to restore position, integer inventory, equity, drawdown and T052
  attribution at the requested cursor.

## Acceptance

For two heterogeneous pool fixtures, the current product backtest entry resolves to
real T100 partitions and refuses the fixed empty event source by named reason.
Successful runs carry a manifest whose `dataset_partition_refs` resolves to the same
canonical bytes T100 registered (verified by content hash, range and PoolKey); a
manifest whose references disagree with T100's registered partitions, or whose
references were authored from an event cursor or a coverage string, is rejected by
named reason and produces no `SUCCEEDED` artifact.

Successful runs carry a simulation evidence artifact whose `block_range` and
`tick_range` are separate fields, agree with the partition's source range and the
dataset's registered reconstruction, and never cross-write one into the other;
the artifact carries position, raw token amounts, integer `liquidity`, realized
fees, cost components, equity, drawdown and T052 attribution components bound to
the actual fill cursor, so a `RunState` reader at that cursor restores them through
the existing T061 engine and T052 attribution semantics and never through a strategy
callback, a range-derived synthetic, or an interpolated tick.

Mismatches on dataset reference / hash, range, PoolKey, registry / schema revision,
transition ordering, cursor or checksum fail closed with named reason codes and
publish no `SUCCEEDED` artifact. Failed, cancelled, incomplete, legacy-only and
binding-mismatched runs publish neither a complete-looking result nor replayable
evidence, and an inspection test proves no current consumer reaches a fixed empty
event source, a cursor-fabricated or coverage-fabricated partition reference, a
block_range conflated into tick_range, or a strategy callback to recover historical
state.

All existing T109 acceptance — same-cursor multi-transition ordering, the three-event
delayed-fill fixture, sparse-checkpoint equivalence, strategy-replacement byte
equivalence, T052 attribution equivalence, legacy unavailable behavior, atomic
publication, shared canonical timeline, T104 fee composition and binding/tamper
matrices—remains passing; the new pipeline-repair tests above are added as
additional acceptance cases.

## Must not

use the fixed empty event source as a current authoritative product backtest entry;
fabricate, invent, infer or downgrade a `dataset_partition_refs` from an event
cursor, a coverage string, a placeholder, a synthetic list or an otherwise non-
resolvable source; conflate `block_range` with `tick_range`; store a `block_range`
value in a `tick_range` field; embed the canonical market timeline in a manifest,
report or evidence; rerun strategy code to recover historical state; create a second
replay, backtest, accounting, fee, manifest, evidence, publication or strategy
authority; publish partial evidence as success; weaken any existing T109 acceptance,
gate, Must-not clause or test assertion; mutate, regenerate, reinterpret, re-rank or
backfill any pre-T112 T069, T105 or T109 record; grant strategy registration, risk
approval, paper or live permission, execution authority or signer activation; or
serialize a private key, signing payload, endpoint secret, webhook credential, `.env`
value, RPC URL or authorization header.
