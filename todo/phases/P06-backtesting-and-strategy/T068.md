# T068 — Register strategy identities with their parameter schema and code provenance

> Phase: `P06`
> Contract status: `OWNER_PLAN_EXTENSION_2026-09-20`

## Dependencies

T060, T062, T065

## Outcome

every strategy a run can execute has one registered identity — parameter schema, version
and code provenance — for the manifest authority to bind published results to, so the T065
adaptive-Range strategy is named instead of being absent from a closed five-name
vocabulary.

## Deliverables

a strategy registry, in the strategy layer of `ARCHITECTURE.md` §2.2, that enumerates
every strategy a backtest or paper run may execute and carries for each one a stable
identity string, a parameter schema (parameter names, types, units and allowed ranges),
a version, and code provenance: the module that implements it and the code revision that
module was built from. Registration covers the T062 baselines and the T065 adaptive-Range
strategy, which no manifest identity names today.

The registry is the deterministic validation surface the manifest authority T105 binds
published manifests to: it answers whether an identity is registered and whether a
parameter set is declared by that identity's schema, so a manifest bound to it cannot be
published with an identity the registry does not carry or with parameters its strategy does
not accept. T105 owns the cutover from the current hard-coded five-name set and the
manifest integration that proves it, so this task publishes and validates no manifest and
cannot become a second manifest publisher. Registry enumeration and its checksum are
deterministic, and the registry is readable without a network call, without the Web entry
point and without reading a strategy's implementation.

## Acceptance

the T065 adaptive-Range strategy has a registered identity, and a lookup by that identity
returns its parameter schema, version and code provenance (test); an identity the registry
does not carry, and a parameter set the registered schema does not declare, are both
rejected by the registry's validation surface instead of being accepted (test); two
enumerations over the same revision return the same order and the same registry checksum,
and every registered identity's code provenance resolves to a module that exists (test);
manifest integration — recording the registered identity, schema, revision and provenance
in a published manifest, and proving the old hard-coded identity path unreachable — is
verified by T105 rather than here; the layer check passes with no new suppression:
`python -m tools.check_imports check` reports no finding for the registry module, and the
registry imports neither the RPC adapter, storage, the signer, nor the Web entry point
(test).

## Must not

accept an unregistered or caller-invented strategy identity, replace a closed definition
with "whatever the caller supplies", supply an identity or parameter-schema check weaker
than the validation the manifest path applies today, register a strategy by symbol or
display name rather than by identity, publish or validate a manifest, or import RPC,
storage, signing or presentation code.
