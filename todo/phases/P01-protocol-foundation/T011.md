# T011 — Model tokens, blocks, transactions, and raw event identity

> Phase: `P01`
> Contract status: `FROZEN_FROM_BASELINE_6C31778`

## Dependencies

T010

## Implementation status

domain records and tests exist; dependency/quality verification is open.

## Outcome

every observation and every pool-level record is uniquely located in a chain history; a chain-agnostic record-level pool identity carries `(chain_id, pool_id, pool_manager_address)` so that downstream registries can disambiguate without altering V4's on-chain 32-byte `PoolId`.

## Deliverables

token/native metadata, `BlockRef`, `TransactionRef`, `EventKey`,
canonical/orphaned/removed status, and deterministic serialization,
and the chain-agnostic `PoolIdentity(chain_id: ChainId, pool_id: PoolId, pool_manager_address: Address)` composite value object whose on-chain `pool_id` bytes are exactly V4's keccak256 ABI-encoded `PoolKey`.

## Acceptance

identity includes chain ID, block hash/number, transaction hash and
log index; collisions across chains/forks are tested; absent/nonstandard token
metadata remains representable without changing identity;
`PoolIdentity` round-trips through `(chain_id, pool_id, pool_manager_address)` and never re-derives the on-chain 32-byte `PoolId` (which remains keccak256 of the ABI-encoded `PoolKey`); cross-chain collision tests use the chain-id placeholder `ChainId(46630)` until T024 verifies the real value, but the type is chain-agnostic on day one; `pool_manager_address` is required at construction time (no default).

## Must not

require symbol/name, use `(tx_hash, log_index)` without chain, or
discard an orphaned identity;
use `PoolIdentity` to replace the V4 on-chain `PoolId` (the latter is keccak256 of the ABI-encoded `PoolKey` and is fixed by V4); construct `PoolIdentity` without `pool_manager_address`.
