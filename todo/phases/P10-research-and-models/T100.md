# T100 — Build the research dataset registry and numeraire qualification

> Phase: `P10`
> Contract status: `OWNER_PLAN_EXTENSION_2026-09-18`

## Dependencies

T034, T039, T053

## Outcome

A named, immutable, versioned dataset spanning one or more pools over declared
block ranges, bound to an explicit reporting numeraire with a recorded valuation
qualification, so that backtests, models and the console all reference the same
object instead of re-deriving their inputs.

This is the object that separates the research universe from the execution scope.
A research dataset may contain many `PoolKey` values and imposes no token approval,
because research neither holds nor trades; it must never grant, feed or weaken the
single-active-pool execution path.

## Deliverables

- A dataset registry: dataset identity, version, content hash, member pools, each
  member's block range, the partitions each member resolves to, and the ingestion
  and schema revisions those partitions carry.
- Immutability and versioning: publishing a dataset creates a new version; an
  existing version is never edited, and an overlapping range is a new version
  rather than a mutation.
- A numeraire hierarchy applied per dataset: USDG first, then a qualified USD
  stablecoin, with ETH reserved for display and explicitly labelled as a volatile
  numeraire. A dataset for which no qualified route exists is reported
  `RELATIVE_ONLY` and carries results in relative terms only.
- A valuation qualification record per dataset: chosen numeraire, source,
  observed-at, available-at, staleness and confidence, with the same point-in-time
  discipline the quote layer already requires.
- A query surface answering what datasets exist, what each covers, which pools and
  ranges it contains, and its qualification status.
- Registry entries that reference the underlying partitions rather than copying
  events, so one acquisition is reusable by many later datasets.

## Acceptance

Two heterogeneous datasets — one single-pool with a USDG numeraire, one multi-pool
with a mixed numeraire — resolve identically across repeated runs and hosts after
excluding declared observational fields; a dataset whose numeraire has no qualified
route is reported `RELATIVE_ONLY`, and no field of a `RELATIVE_ONLY` dataset may
contain a USD-denominated PnL value; a dataset containing a pool below `backtest`
support level is rejected with a named reason; adding a pool or extending a range
produces a new version while the prior version stays byte-identical; two datasets
covering the same partitions remain isolated, and a result computed on one is never
attributed to the other; and every dataset records the numeraire's provenance and
availability time.

Boundary and invalid-input cases covered: a pool list that is empty, duplicated, or
contains an unknown `PoolKey`; a block range that is inverted, exceeds the pool's
observed life, or spans a gap; a numeraire that is the pool's own token; a
stablecoin whose qualification has expired; and a stale or conflicting valuation
source.

## Must not

Convert internal simulation state into the numeraire, or store numeraire-converted
values as the canonical record; merge several pools into one ledger, one position or
one coverage claim; let a research dataset acquire execution authority, appear as an
approved pool, or feed the active-pool path; assume a stablecoin equals one dollar;
present a `RELATIVE_ONLY` result as a USD result; or mutate a published dataset
version.
