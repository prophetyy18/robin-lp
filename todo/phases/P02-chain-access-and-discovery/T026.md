# T026 — Add pool-first onboarding and the research universe registry

> Phase: `P02`
> Contract status: `OWNER_PLAN_EXTENSION_2026-09-19`

## Dependencies

T022, T024

## Outcome

A complete, idempotent PoolKey registry that accepts a pool by target token, by full
V4 `PoolKey`, or by `PoolId`, and that holds a **research universe** — any number of
pools across different pairs, fees, tick spacings and hooks — separately from the
single active execution pool.

This contract supersedes T022: it restates that task's full obligation set and adds
the pool-first entry and research-universe membership. T022's implementation is live
and expected to be reused, cited and extended rather than rewritten; T022 itself is
retired as a governing contract so that one contract, not two, describes this area.

Registry entry is by three paths, all reconciled against the chain before a record is
written. A full V4 `PoolKey` has its `PoolId` derived locally and reconciled against
the `Initialize` event the chain emitted. A `PoolId` is a one-way digest, so it is
resolved by scanning `Initialize` events for a matching indexed `PoolId` and then
verifying the decoded `PoolKey` derives back to it. A target token address follows the
existing discovery path.

Uniswap V4 pools are entries in the singleton `PoolManager`; they are not contracts,
so **a 20-byte address is never a pool identity** (ADR-014).

## Deliverables

- The Initialize decoder and scanner, derived-ID verification, the registry with its
  provenance and scan coverage, and the defensive token metadata reader, all preserved
  from T022.
- Pool-first entry by full `PoolKey`: local `keccak256(abi.encode(PoolKey))` derivation
  reconciled against the on-chain `Initialize` event.
- Pool-first entry by `PoolId`: an `Initialize` scan keyed on the indexed `PoolId`,
  with the decoded `PoolKey` verified back to that digest.
- Explicit rejection, with a reason, of any 20-byte address supplied as a pool
  identity, including another protocol version's pool, a position NFT, a front-end
  link and the `PoolManager` itself.
- Research-universe membership: an arbitrary set of `(chain_id, PoolKey)` members,
  each carrying its own block range and its own support level, kept distinct from the
  single active execution pool and never conflated with it.
- A registry query surface answering which pools are members, on which entry path they
  were added, and whether a pool is an execution candidate, a research member, or both.

## Acceptance

Stop, resume and overlapping scans produce identical registries; native currency,
broken, reverting and oversized metadata, dynamic fee, nonzero hook, duplicates and
conflicting `Initialize` data are covered and a conflict fails closed; a pool added by
full `PoolKey` and the same pool added by `PoolId` resolve to one registry entry with
identical fields; adding the same pool twice by two different paths is idempotent; a
`PoolId` that no `Initialize` event matches stops with a named reason rather than
registering a partial record; a 20-byte address input is rejected with a reason; two
pools sharing a currency but differing in fee, tick spacing or hooks remain distinct
entries; and a research-universe member is never reported as, or promoted by, the
active execution pool.

Boundary and invalid-input cases covered: a pool whose `Initialize` lies outside the
scanned range; two `Initialize` events matching one `PoolId`; a `PoolKey` supplied with
its currencies in the wrong order; a `PoolKey` whose derived `PoolId` disagrees with
the chain; a research universe that is empty; and a member list containing a duplicate.

## Must not

Query a factory (V4 is singleton); discover by token symbol; accept a 20-byte address
as a pool identity; infer a `PoolKey` from a `PoolId` without an on-chain `Initialize`
match, or reorder currencies to make a supplied `PoolKey` fit; drop pools whose
metadata call fails; merge research membership into the active execution pool; or let
a research-universe entry grant, or be readable as granting, any execution authority.
