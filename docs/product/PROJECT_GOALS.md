# 项目目标基准

状态：草案，逐步确认中
最后更新：2026-09-13

## 1. 文档用途

本文档定义项目为什么存在、最终要实现什么，以及如何判断实现是否仍在
朝目标前进。它不描述具体实现步骤；任务拆分、依赖关系和验收命令仍由
`TODO.md` 管理。

只记录已经确认的目标。尚未确认的产品选择放在“开放问题”中，不提前
写成既定需求。

## 2. 项目使命

为个人用户构建一个覆盖历史研究、实时虚拟交易、策略信号、风险管理、
可视化监控和最终自动执行的 Uniswap V4 LP 管理系统。

系统应基于可验证的链上数据：

1. 重建目标 token 相关池的历史状态；
2. 展示策略在历史回测中的收益、成本和风险；
3. 展示策略在实时虚拟交易中的信号、持仓和结果；
4. 在通过审批和风险验证后，按照策略自动完成 LP 与必要的 token 交易；
5. 使数据、决策、收益和链上操作可验证、可解释、可复现、可审计、可暂停。

盈利不是软件正确性的验收条件。系统必须能够如实展示亏损、失败策略和
不适合提供流动性的结论。

## 3. 目标用户与运行形态

### 3.1 目标用户

V1 首先服务系统所有者本人。V1 不以公众注册、多租户 SaaS 或策略市场为
目标，但必须具备良好的可视化、文档和交付质量，不能退化为只能由开发者
操作的脚本集合。

### 3.2 运行形态

系统采用“服务器后台持续自主运行 + Web 控制台管理”的形态。

后台系统负责持续进行数据采集、状态重建、策略运行、信号生成、风险检查、
虚拟或真实执行、失败恢复和账本核对。浏览器关闭或 Web 服务重启不得中断
这些职责。

Web 控制台负责观察、配置、比较、审批、审计和紧急控制。Web 界面不得直接
接触私钥，也不得成为后台持续运行的必要条件。

## 4. V1 范围

V1 的限制单位是一个**目标 token**，不是一个池。

一个目标 token 可以对应多个不同的 Uniswap V4 `PoolKey`，包括不同的配对
token、fee、tick spacing 和 hook。系统需要分别发现、验证、分析和展示这些
池，而不能把它们视为同一个池，也不能假定它们具有相同风险。

V1 不同时研究或管理多个目标 token 主题。目标 token 的确切切换和重新审批
规则尚待定义。

## 5. 产品能力路径

系统按照以下能力路径发展：

`链上数据 → 历史重建 → 策略回测 → 实时信号 → 虚拟交易 → 风险验证 → 自动执行 → 持续监控`

必须清楚区分以下三个环境：

- **历史回测：**回答策略在过去、仅使用当时可获得的信息时会得到什么结果。
- **实时虚拟交易：**记录策略现在产生的信号，以及模拟执行后的持仓和结果。
- **真实自动执行：**记录实际提交的 LP/Swap 操作、链上回执、真实仓位和余额。

三种环境应尽量共享策略、风险和账本接口，但其数据和结果不得在界面、报告
或审计记录中混淆。

## 6. 自动化授权边界

系统采用策略级授权，而不是逐笔交易授权。

用户审批策略版本、适用链和池、资金上限、token 敞口、允许的操作类型、
滑点/Gas/损失/回撤限制及关键参数。审批通过后，后台可以在授权范围内自动
执行日常操作，不要求用户逐笔确认。

最终自动操作范围包括：

- 必要的 token Swap 和资产配比调整；
- 创建 LP 仓位；
- 增加或减少流动性；
- 领取和按策略复投费用；
- 价格出区间后的再平衡；
- 风险降仓、策略退出和预先授权的保护性撤出；
- 交易确认、失败处理、状态恢复和账本核对。

以下变化至少需要重新审批：策略逻辑或版本、目标链或 PoolKey、hook 代码或
代理实现、资金或风险上限提高、新增操作权限，以及从 paper 晋级到 live。

控制优先级为：

`人工紧急停止 > 集中风险限制 > 已批准策略 > 自动执行`

## 7. Token 与 Pool 资格审批

系统必须将三类批准分开：

`目标 token 获批 ≠ 配对 token 获批 ≠ PoolKey 获批`

### 7.1 Token 级资格

目标 token 和每个配对 token 都必须形成独立的、带时间和来源的资产尽调
档案。档案至少覆盖：

- 链、合约地址、字节码、代理实现和升级权限；
- 增发、暂停、冻结、黑名单、交易税、fee-on-transfer、rebasing 等能力；
- 管理员、多签、timelock、源码验证、审计及安全事件；
- 总供应、流通、holder 集中度、团队/投资人份额、锁仓和未来解锁；
- 流动性、交易深度、波动、可操纵性和稳定币脱锚风险；
- 官方资料、治理公告、可信安全报告及外部舆情证据。

外部舆情只能作为带来源、时间和可信度的风险证据，不能单独依据热度或情绪
分数自动批准或否决资产。

Token 批准需要明确允许的行为，例如：是否允许持有、用于 LP、自动 Swap，
以及最大敞口。批准必须绑定链和合约身份，不能绑定 token symbol。

### 7.2 Pool 级资格

每个 `PoolKey` 必须单独检查 PoolManager 部署、配对资产资格、fee、tick
spacing、hook 代码与行为、数据完整性、流动性、可操纵性和策略适用性，并
分别决定是否允许 ingestion、backtest、paper 或 live。

Token 获批不能使相关池自动获批；一个池获批也不能使同币对的其他 PoolKey
自动获批。

### 7.3 持续监控与失效

代码或代理实现变化、管理权限变化、异常增发/解锁、holder 或流动性显著
集中、稳定币脱锚、严重安全事件以及可信风险公告，都应触发告警。达到规定
条件时必须暂停新增风险，并使原批准失效或进入人工复核。

## 8. 当前已确认的目标

- `G-RESEARCH-01`：基于可验证数据产生可复现的历史 LP 策略结果。
- `G-PAPER-01`：在实时虚拟交易中展示真实时序下的信号、持仓、收益和风险。
- `G-UI-01`：提供用于观察、配置、比较、审批、审计和紧急控制的 Web 控制台。
- `G-AUTO-01`：后台不依赖 Web 会话，能够持续运行并从故障中恢复。
- `G-AUTH-01`：通过版本化的策略授权控制自动执行范围。
- `G-RISK-01`：所有自动操作经过独立、集中且不可绕过的风险检查。
- `G-CONTROL-01`：支持人工暂停、接管和预授权的保护性退出。
- `G-SCOPE-V1`：V1 围绕一个目标 token，覆盖该 token 对应的多个 V4 池。
- `G-TOKEN-01`：目标 token 和所有配对 token 分别完成资产资格审批。
- `G-POOL-01`：每个 PoolKey 独立完成数据、hook、经济性和执行资格审批。
- `G-COMPARE-01`：横向比较相关池的历史收益、paper 表现、风险和资金效率。
- `G-LIVE-01`：最终在明确授权范围内自动完成 LP 与必要的 Swap 操作。

## 9. 开放问题

以下内容尚未确认：

- V1 的确切目标链，以及是否只允许一个链；
- 是否自动发现目标链上所有包含目标 token 的 V4 池；
- 哪些 token 风险属于不可绕过的硬性否决，哪些允许用户接受；
- 配对 token 的默认允许行为和最大风险敞口；
- 多个获批池之间是否以及如何自动选择和分配资金；
- 目标 token 的切换、审批有效期和定期复审规则；
- V1 Web 控制台必须包含的页面和操作；
- 历史回测、paper 和 live 各自的量化成功标准；
- live 所需的钱包托管、人工接管与紧急退出方式。
