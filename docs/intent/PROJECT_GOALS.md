# V1 项目目标与验收基准

状态：草案，逐步确认中
最后更新：2026-09-16

## 1. 文档用途

本文档只定义 V1 为什么存在、V1 要实现什么，以及如何判断当前实现是否仍在
朝 V1 目标前进并最终达到 V1 标准。它不提前定义 V2 或更远版本，也不描述
具体实现步骤；任务拆分、依赖关系和验收命令仍由 `todo/README.md` 管理。

只记录已经确认的目标。尚未确认或已明确延期的产品选择必须标出决策阶段，
不提前写成既定需求。

## 2. V1 项目使命

V1 为个人用户构建一个覆盖历史研究、实时虚拟交易、策略信号、风险管理、
可视化监控和最终自动执行的 Uniswap V4 LP 管理系统。

系统应基于可验证的链上数据：

1. 重建目标 token 相关池的历史状态；
2. 展示策略在历史回测中的收益、成本和风险；
3. 展示策略在实时虚拟交易中的信号、持仓和结果；
4. 在通过审批和风险验证后，按照策略自动完成 LP 与必要的 token 交易；
5. 使数据、决策、收益和链上操作可验证、可解释、可复现、可审计、可暂停。

盈利不是软件正确性的验收条件。系统必须能够如实展示亏损、失败策略和
不适合提供流动性的结论。

## 3. 目标用户与运行形态

### 3.1 目标用户

V1 首先服务系统所有者本人。V1 不以公众注册、多租户 SaaS 或策略市场为
目标，但必须具备良好的可视化、文档和交付质量，不能退化为只能由开发者
操作的脚本集合。

### 3.2 运行形态

系统采用“服务器后台持续自主运行 + Web 控制台管理”的形态。

后台系统负责持续进行数据采集、状态重建、策略运行、信号生成、风险检查、
虚拟或真实执行、失败恢复和账本核对。浏览器关闭或 Web 服务重启不得中断
这些职责。

Web 控制台负责观察、配置、比较、审批、审计和紧急控制。Web 界面不得直接
接触私钥，也不得成为后台持续运行的必要条件。

## 4. 目标 Token、候选池与活动池

V1 只支持 Robinhood Chain，不把其他 EVM 链纳入产品交付范围。系统仍必须
保存并校验 chain ID，防止连接错误网络或混淆不同网络的数据，但不要求 V1
提供切换到其他 EVM 链的产品能力。

Robinhood Chain mainnet 与 testnet 的职责明确分开：

- testnet 用于集成测试、交易流程验证、失败恢复和安全演练；测试 ETH 可用于
  支付测试交易 Gas；
- mainnet 用于真实历史研究、实时数据、paper trading，以及完成独立审批后
  的真实自动执行；
- testnet 上的价格、流动性、收益和策略表现不得作为 mainnet 经济有效性的
  证明；
- testnet 验证通过是进入 mainnet 自动执行的必要条件，但不是充分条件。

V1 在同一运行配置中围绕一个**目标 token**工作。系统可以发现该 token 的
多个候选池，但同一时间只能有一个由用户选择的**活动 PoolKey**进入策略、
paper trading 或真实自动执行。

一个目标 token 可以对应多个不同的 Uniswap V4 `PoolKey`，包括不同的配对
token、fee、tick spacing 和 hook。系统需要分别发现、验证、分析和展示这些
池，而不能把它们视为同一个池，也不能假定它们具有相同风险。

目标 token 必须由用户人工输入其 Robinhood Chain contract address，并由
用户明确审批。系统不得自行选择目标 token，也不得根据收益、热度、舆情或
其他信号自动切换目标 token。

切换目标 token 是一项明确的人工操作：由用户输入并确认新的 contract
address，随后对新 token 重新执行资格调查与审批。旧目标 token 的研究和
交易历史必须保留，不能因切换而被覆盖或与新 token 的结果混合。

目标 token 获批后，系统应从经过验证的 Robinhood Chain Uniswap V4
`PoolManager` 历史中自动发现所有包含该 token 的 `PoolKey`。发现不能依赖
token symbol、前端列表或人工逐个输入池；用户可以手动触发重新扫描和核查。

Web 控制台必须展示发现的全部候选池，包括尚未获批、不受支持或被拒绝的池，
并至少展示：

- 完整 `PoolKey`、`PoolId`、所在环境和初始化区块；
- 配对 token 的 contract address、symbol/decimals 等显示信息和审批状态；
- 静态或动态 fee、观测到的实际 fee，以及 tick spacing；
- `PoolManager`、hook、StateView 等相关 contract 地址、代码身份和验证状态；
- hook flags、已知行为、升级权限和支持等级；
- 历史流动性、交易量、数据覆盖、异常和风险摘要；
- 系统判断该池可用于 discovery、backtest、paper 或 live 的理由。

用户通过 Web 页面从候选池中明确选择一个可信任、允许进入策略的活动
`PoolKey`；界面必须采用单选语义，不能让 V1 同时启用多个池。系统必须记录
选择时的 PoolKey、相关 contract/code hash、token 审批版本、时间和授权人。
用户可以随时撤销选择。

池成为活动池必须同时满足：系统的必要技术与安全资格检查通过、目标 token
和配对 token 获批、用户明确选择。用户选择不能绕过不可接受的技术或安全
失败；系统也不能仅根据收益排名代替用户选择。

V1 不同时运行多个池的策略，不在池之间自动分配或转移资金，也不自动切换
活动池。更换活动池必须由用户人工选择并重新确认相关授权；旧池的历史、
回测、paper 和交易记录必须保留且与新池隔离。

## 5. 产品能力路径

系统按照以下能力路径发展：

`链上数据 → 历史重建 → 策略回测 → 实时信号 → 虚拟交易 → 风险验证 → 自动执行 → 持续监控`

V1 的短周期历史研究必须提供一条不要求自建节点或付费 RPC 套餐的可运行路径：
以 Robinhood 官方公共 RPC 和用户配置的 Alchemy 免费 endpoint 组合完成读取，
并根据每个 endpoint 当次探测到的日志范围、archive state、finality、限流和可用性
分工。免费额度或公共服务不是完整性保证；任一能力变化、预算超限或交叉验证
失败都必须显式停止或降级，不能用缺失数据继续回测。付费 endpoint 和自建节点
可以作为以后替换的传输能力，但不得改变数据完整性与可复现语义。

必须清楚区分以下三个环境：

- **历史回测：**回答策略在过去、仅使用当时可获得的信息时会得到什么结果。
- **实时虚拟交易：**记录策略现在产生的信号，以及模拟执行后的持仓和结果。
- **真实自动执行：**记录实际提交的 LP/Swap 操作、链上回执、真实仓位和余额。

三种环境应尽量共享策略、风险和账本接口，但其数据和结果不得在界面、报告
或审计记录中混淆。

V1 可以在研究和回测中保存、运行并比较多个策略及参数版本，但同一时间只能
有一个由用户人工选择和批准的活动策略版本进入实时 paper 或 live 执行。活动
策略必须绑定完整策略逻辑、参数、代码版本、数据要求、目标 PoolKey 和风险
授权，不能只绑定一个可被覆盖的策略名称。

系统不得根据近期收益、排名或信号自动切换活动策略。更换策略逻辑、参数或
代码版本是一项人工操作，新版本必须重新生成回测证据，并按 preliminary paper、
testnet、post-testnet paper/shadow 和 live 的适用门槛重新批准；旧版本的结果和审计历史
必须保留。preliminary paper 通过不代表可以跳过 testnet 或正式 paper/shadow 门槛。

系统可以按照预先声明的参数空间自动生成候选策略版本，运行回测、稳健性和
样本外验证，并产生可解释的排序或推荐。推荐必须同时展示收益、最大回撤、
Gas、换手、资金效率、参数敏感性和样本外表现，不能只按最高收益选择，也不能
隐藏失败或亏损候选。自动推荐只是一项研究输出，不产生 paper 或 live 权限；
最终活动版本必须由用户人工选择并批准。

V1 策略产生入场、区间、再平衡和退出决策时，市场信号只使用决策时刻已经
可获得的价格、交易量和池内流动性分布。活动池提供原始相对价格、交易量和
流动性分布；所有 USDG 收益率、估值和 5 分钟极端涨跌判断，使用 T053 筛选并版本化的
合格 point-in-time USDG 价格换算。该换算只是价格语义的一部分，不得藉此引入 token
团队、holder、社交舆情、新闻、项目标签或其他外部基本面作为策略信号。Token 合约、
hook 和项目背景仍用于准入、风险阻断和展示，不能被策略当作预测因子绕过边界。

Pool fee、Gas、滑点、税费和 hook 结算影响必须进入回测成本、PnL 与执行风险，
但不属于 V1 的方向预测信号。V1 的推荐只能说明在既定历史数据和假设下的相对
结果，不能宣称找到了适用于该 token 的“最佳”或保证盈利策略。

V1 以 USDG 为唯一主要计价和策略目标，目标 token 是 LP 期间承担的库存，不以
token 上涨作为策略必须成立的盈利来源。主要基准是同期保持 USDG；HODL 与理想
再平衡/LVR 作为归因基准保留。策略先通过基本面/合约准入与风险预算，再使用
价格、交易量和流动性分布识别下跌、跳跃、趋势和 Range 状态，最后只在保守
预期手续费优势能够覆盖库存风险、LVR 与全部执行成本时产生入场候选。

首个版本采用可解释的规则或统计基线。模型、特征、窗口和阈值可以在后续实验中
调整，但必须版本化、可复现并重新验证；USDG 账本口径、时间可用性、硬门槛、
风险网关和审计接口不得随模型调整而漂移。详细规则以
[`STRATEGY_ECONOMICS.md`](../specs/STRATEGY_ECONOMICS.md) 为准。

V1 的主要策略方向是自适应区间 LP：使用决策时已知的价格变化确定候选区间
中心与宽度，使用交易量和流动性分布判断入场机会、区间拥挤程度及再平衡价值。
策略必须覆盖从等待入场、建立仓位、区间内运行、离开区间、等待价格自然返回、
撤出、换币重建、冷却到最终退出的完整生命周期。

价格离开区间只产生 `OUT_OF_RANGE` 状态，不自动等同于减少流动性、换币、
重建仓位或退出策略。策略必须允许继续持有原仓位并等待价格重新进入区间；也
可以在满足版本化条件时选择只撤出流动性、撤出后换币并建立新区间，或完全退出。
这些动作是不同决策，必须分别记录原因、时间和成本。

回测必须以每次完整持仓 episode 为单位重建净值曲线：从入场前资产开始，逐项
记录 LP 中的 token 库存、区间内实际费用、区间外持有期间的价格变化、未复投
费用、撤流动性、领取、Swap、重新 Mint 的 Gas/滑点/税费/hook 影响，以及最终
退出后的资产价值。离开区间后仍须按实际单边库存持续估值，不能把仓位冻结，
也不能假设费用继续产生或自动复投。

对于同一段离开区间历史，研究报告应比较至少四条反事实路径：始终等待原区间、
立即重建、等待固定确认条件后重建、按照成本收益条件重建或退出。反事实用于
解释策略取舍，实际策略在当时只能使用已经发生的数据，不能利用后来是否反弹
来决定当时动作。

V1 不以完成回测或 paper trading 作为最终交付。回测、testnet 和 paper 是
进入 live 的逐级证据门槛；只有系统能够在 Robinhood Chain mainnet 上，针对
一个经批准的活动 PoolKey，在策略授权和资金上限内真实执行并核对 LP/Swap
操作，V1 才达到最终能力边界。任何一级未通过时，系统只能停留在已获批准的
较低能力等级，不能通过配置开关跳级。

为了尽早验证实时数据、策略、风险和账本接口，工程上允许在 testnet 前运行
preliminary paper。这只是实现验证，不产生 live 资格。live 的正式证据顺序仍为：
backtest → testnet → post-testnet paper/shadow → 安全复核 → 人工晋级。

V1 的 live 完成不要求策略盈利，但至少要求：真实交易只作用于获批链、合约、
PoolKey 和操作；链上回执、仓位、余额、费用与内部账本能够核对；重启、超时、
交易替换和链重组不会造成重复经济动作；风险限制和人工紧急停止能够阻止新增
风险，并存在经过演练的降仓或退出路径。

## 6. 自动化授权边界

系统采用策略级授权，而不是逐笔交易授权。

用户审批策略版本、适用链和池、资金上限、token 敞口、允许的操作类型、
滑点/Gas/损失/回撤限制及关键参数。审批通过后，后台可以在授权范围内自动
执行日常操作，不要求用户逐笔确认。

V1 使用一个独立、限额的 EOA 执行钱包。私钥以标准 Web3 Secret Storage
加密 Keystore 文件保存，Keystore 可以备份，但解密密码不得保存到项目配置、
`.env`、数据库、启动参数、日志或 Web 页面中。

执行钱包默认由系统提供的本地交互式工具全新生成，并在同一进程内立即加密
写入 Keystore；工具不得显示、打印或返回原始私钥。V1 同时允许用户显式选择
导入一个已有私钥，但私钥只能通过不回显的交互式终端提示输入，导入完成后
同样只保存加密 Keystore，不得从命令参数、环境变量、文件或 Web 接收明文。

启动独立签名服务时，由用户本人在不会回显的交互式终端提示中输入密码。
签名服务只在自身隔离进程的内存中解密并持有私钥；Web、策略、研究、风险和
其他后台进程只能提交经过风险检查、交易预执行和授权范围校验的确定性签名
请求，不能读取、导出或显示私钥。签名服务或服务器重启后必须回到锁定状态，
由用户再次人工解锁；V1 不保存能够在无人输入密码时自动解锁 Keystore 的秘密。

系统生成执行钱包后只展示其公开地址，资产由用户从系统之外人工转入。V1
不得连接、导入、请求签名或以任何方式控制用户的主钱包。系统只能使用 live
审批中明确授权给执行钱包的资金额度；若观测到的钱包余额或资产超出已批准的
范围，超出部分不得被自动视为可用资金，也不得用于增加流动性、新增投入或
费用复投。现有仓位仍按已批准策略运行，其正常 Swap、再平衡和退出仍分别受
操作权限、敞口、滑点、Gas 和其他风险限制约束。

V1 的资金、敞口、单笔操作、损失和回撤限制统一使用 USDG 等值进行审批和
展示，同时账本必须保留每种 token 与 ETH 的原始整数数量。USDG 只是计价单位，
不代表目标 token 或配对 token 必须存在可交易到 USDG 的 route；“能否可靠
估值”和“能否实际兑换为 USDG”必须作为两个独立状态展示。

USDG 估值必须记录价格来源、观测时间、可用时间、路径、置信等级和有效期。
可以使用已验证的独立预言机，或由具备足够质量的价格来源组合换算；不得只依赖
活动池可被操纵的即时价格，也不得固定假设 `1 USDG = 1 USD`。如果某项资产
没有合格的 USDG 估值来源，系统不得新增 LP、Swap、增仓或其他新增风险，但仍
必须允许减少/移除 LP、领取资产、撤销授权和紧急退出。

Gas 储备和 Gas 消耗必须分别审批与记录。用户以 USDG 等值批准 Gas 储备范围、
单笔、每日和累计 Gas 预算；系统同时保留实际 ETH 余额、`gasUsed`、
`effectiveGasPrice`、交易哈希以及各自采用的 ETH/USDG 估值证据。Gas 预算不能
与 LP 投入额度或策略损益合并成一个不可核对的数字。

资金限制采用全局与策略两层控制。全局钱包上限限制执行钱包可被系统使用的
USDG 等值总资产；策略授权上限分别限制当前获批策略的 LP 投入、目标 token
敞口、单笔操作金额和每日累计周转。每次决策必须同时通过两层检查，实际允许
值取两者中更严格的限制，策略或执行模块均不得覆盖全局限制。

提高任何全局或策略上限都必须生成新版本并由用户重新人工审批；降低上限可以
立即生效。资金上限是新增投入与重新进入 LP 时的配置上限，不是持续盯市的
强制清算线。现有仓位因价格上涨或上限降低而超过限额时，只停止增加流动性、
新增风险和费用复投，不立即退出或强制卖出；现有仓位继续按照已批准策略的
交易、再平衡和退出规则运行。

策略下一次退出后重新进入 LP，或通过一次完整再平衡重新建立仓位时，必须按
当时有效的全局与策略上限重新计算，最终投入不得超过更严格的上限。如果已经
没有剩余额度，本次不得增加投入。领取、减少流动性、退出和撤销授权始终不能
仅因为当前仓位超过投入上限而被阻止。

对于 Uniswap V4 集中流动性仓位，降低任一 token 的敞口上限时，系统必须保持
已批准的 `tickLower`/`tickUpper` 不变，并缩小同一个 `liquidityDelta`。在当前
`sqrtPriceX96` 下重新使用固定版本的 V4 整数数学计算所需 `amount0` 和
`amount1`；不得只削减一边、按显示层 USD 比例近似，或为了迁就限额暗中改变
Range。价格位于区间内时两边随同一流动性规模缩小；位于区间外时新增仓位本来
就只需要其中一种 currency，这不应被伪装成“双边等额”。

仓位规模必须同时满足目标 token、配对 token 和总资金上限，并按价格到达区间
两端后的单边库存计算两种 token 各自的最坏敞口。计算还必须包含钱包中未投入
余量、已计费用以及该 PoolKey 的 Hook 对 `BalanceDelta` 的影响。若任一 currency
是 V4 canonical native ETH，能够投入 LP 的余额必须先扣除独立批准的 Gas 储备。
最终交易使用明确的 liquidity、两边最大投入、deadline 和预执行结果约束；整数
舍入后的任一边不得突破上限。缩小后若预期收益不再覆盖 Gas、滑点、动态 fee、
Hook 成本和最小经济仓位要求，则本次不进入，不自动改变 Range 或提高限额。

紧急退出默认只负责撤销未决新增风险、减少或移除 LP、领取可领取资产并撤销
相关授权，退出所得资产保留在执行钱包。V1 不自动将资产转往主钱包、交易所
或其他外部地址；后续转移由用户在系统之外人工完成。

V1 自动操作范围包括：

- 必要的 token Swap 和资产配比调整；
- 创建 LP 仓位；
- 增加或减少流动性；
- 领取和按策略复投费用；
- 价格出区间后的再平衡；
- 风险降仓、策略退出和预先授权的保护性撤出；
- 交易确认、失败处理、状态恢复和账本核对。

以下变化至少需要重新审批：策略逻辑或版本、目标链或 PoolKey、hook 代码或
代理实现、资金或风险上限提高、新增操作权限，以及从 paper 晋级到 live。

策略 live 授权一经批准持续有效，不要求按日或按固定周期重新审批。用户主动
撤销，或者策略版本、PoolKey、执行钱包、获批合约/代码身份、允许的操作发生
变化，以及资金或风险上限提高时，授权必须立即失效并等待重新审批。系统可以
提示用户定期复核，但仅到达提醒日期不能自动停止一个其他条件仍然有效的策略。

持续策略授权不等于永久有效的交易请求。每个具体签名请求仍必须绑定当前授权
版本、nonce、预执行结果和较短 deadline；过期、重复或绑定状态改变的请求不得
签名或广播。签名服务重启后，无论策略授权是否仍有效，都必须由用户重新输入
密码解锁。

控制优先级为：

`人工紧急停止 > 集中风险限制 > 已批准策略 > 自动执行`

系统安全暂停分为两级。临时数据/RPC/估值或签名服务可用性问题进入可恢复暂停：
停止新增风险，继续数据补齐与交易跟踪，在原因消失并通过完整核对后可以自动
恢复。合约/Hook 代码身份变化、PoolKey/链身份冲突、账本或钱包状态无法核对、
未知交易/nonce、密钥疑似泄露、风险服务失效或持续链分歧进入锁定式暂停：
停止新增风险且不得自动恢复，必须由用户查看证据并人工决定恢复、减仓或退出。
两级暂停都不得仅因为异常发生而自动清仓。

运行控制采用 `RUNNING`、`PAUSED_RECOVERABLE`、`LOCKED_REVIEW`、
`MANUAL_CONTROL`、`EXITING` 和 `SAFE_HOLD` 的显式状态。市场风险只可按已批准
策略自动退出；合约/Hook、身份、账本、钱包、nonce、密钥和未知执行语义异常
默认锁定并通知，不盲目自动退出。人工接管必须先冻结新意图、核对 pending
交易与链上状态，再由用户选择并重新模拟风险降低动作；退出成功不能自动恢复
策略。详细规则以 [`OPERATOR_CONTROL.md`](../specs/OPERATOR_CONTROL.md) 为准。

进入任一级暂停、暂停等级升级以及暂停解除时，系统必须通过用户配置的企业微信
群机器人发送通知。Webhook URL 视为秘密，只能在部署时通过秘密配置注入，不得
写入仓库、数据库、普通配置、审计正文或日志。通知发送失败不能阻止或延迟安全
暂停；系统必须持久记录待发送事件、限速重试并去重，避免同一暂停持续刷屏。

通知只包含诊断所需的非秘密字段，例如环境、PoolId/活动策略版本、暂停等级、
原因代码、首次发生时间、当前动作和 Web 控制台链接；不得包含 webhook、私钥、
Keystore 密码、RPC 凭据、原始签名请求或其他认证材料。

## 7. Token 与 Pool 资格审批

本节定义稳定的产品目标；详细、可测试的准入要求以
[`ASSET_ADMISSION.md`](./ASSET_ADMISSION.md) 为准。

系统必须将三类批准分开：

`目标 token 获批 ≠ 配对 token 获批 ≠ PoolKey 获批`

### 7.1 Token 级资格

目标 token 和每个配对 token 都必须形成独立的、带时间和来源的资产尽调
档案。档案至少覆盖：

- 链、合约地址、字节码、代理实现和升级权限；
- 增发、暂停、冻结、黑名单、交易税、fee-on-transfer、rebasing 等能力；
- 管理员、多签、timelock、源码验证、审计及安全事件；
- 总供应、流通、holder 集中度、团队/投资人份额、锁仓和未来解锁；
- 流动性、交易深度、波动、可操纵性和稳定币脱锚风险；
- 官方资料、治理公告、可信安全报告及外部舆情证据。

其中只有保证链、合约身份、会计和交易执行正确性所必需的信息属于强制要求。
团队身份、holder 标签、精确流通量、锁仓/解锁、审计和舆情等外部信息采用
best-effort 获取：能从可追溯来源取得就展示，无法取得就明确标记不可获得，
不自动否决，也不得猜测或伪造。

外部舆情只能作为带来源、时间和可信度的风险证据，不能单独依据热度或情绪
分数自动批准或否决资产。

已经识别且能被系统正确处理的 mint、pause、blacklist、tax、upgrade 等管理
权限不自动构成硬性否决。系统必须完整展示权限、控制者、限制、历史使用和
最坏影响，由用户决定接受、附条件接受或拒绝。

Token 批准需要明确允许的行为，例如：是否允许持有、用于 LP、自动 Swap，
以及最大敞口。批准必须绑定链和合约身份，不能绑定 token symbol。

配对 token 在审批前默认 `HOLD=false`、`LP=false`、`AUTO_SWAP=false`。选择活动
池时，用户必须明确批准 `HOLD` 和 `LP`；`AUTO_SWAP` 始终单独批准，不能因允许
LP 自动获得。配对 token 的默认最大敞口等于当前策略获批的 LP 资金上限，因为
集中流动性仓位离开区间后可能转化为几乎全部配对 token；用户可以设置更低的
USDG 敞口，此时系统按固定 Range 缩小整个 V4 流动性仓位，不能只削减配对侧。

用户通过 Web 控制台分别调整目标 token 和配对 token 的 `HOLD`、`LP`、
`AUTO_SWAP` 权限及 USDG 最大敞口。权限修改先形成草稿，系统展示当前余额/
仓位、依赖关系、受影响策略和授权失效结果；用户完成身份验证和明确确认后，
系统才生成不可变的新权限版本。`LP` 和 `AUTO_SWAP` 必须以 `HOLD` 为前提，但
界面不能在用户不知情时自动扩大权限。

提高权限或敞口属于风险增加，必须使相关 live 授权失效并重新审批。降低权限
立即阻止对应的新操作，但不自动清仓：关闭 `AUTO_SWAP` 停止新自动 Swap；
关闭 `LP` 停止新建、增加和复投，同时保留领取、减仓和退出；关闭 `HOLD` 时
如果钱包或退出流程仍会收到该 token，系统显示未处置余额、停止新增风险并允许
完成风险降低操作，不能假装余额已经消失。

Web 是权限调整的唯一正常入口。V1 可以提供故障排查用的只读 CLI 来查看当前
权限版本和审计记录，但 CLI 不得绕过 Web 审批或直接修改权限。

Token 资格审批默认不设置按天、按月或其他固定日历到期时间。只要审批所绑定的
链、contract address、runtime code、代理 implementation/facet、关键管理权限、
系统已建模的 Token 行为和硬性技术门槛没有变化，用户没有主动撤销，审批就持续
有效。系统可以设置定期复核提醒，但提醒日期本身不得让审批自动失效或中断一个
其他条件仍然有效的策略。

代码或代理实现、关键权限、已建模行为或技术硬门槛发生变化时，原审批立即失效，
停止新增风险，并要求基于新证据重新调查和人工审批。可信安全事件、异常增发或
解锁、holder/流动性显著集中、稳定币脱锚等项目风险发生实质变化时进入
`REVIEW_REQUIRED`，在用户完成复核前同样不得新增风险。短暂的数据源或监控故障
只进入“无法验证”的安全暂停，不得悄悄撤销或续期审批；只有重新取得证据并证明
绑定状态未变化后才可恢复。所有提醒、暂停、失效、复核和撤销都必须保留不可变
审计记录。

Token 资格审批必须包含不可由用户勾选绕过的硬性门槛。人工审批用于接受
已被系统准确识别和展示的剩余风险，不得把身份不明、行为无法验证或系统
无法正确处理的资产强行提升为可交易状态。

V1 的硬性否决边界是“系统能否证明身份、正确执行、正确记账并保留安全退出
能力”。无法确认链/合约/实际执行代码身份，Token 行为无法被系统正确识别、
模拟或记账，已确认 honeypot、无法卖出或无法安全退出，能够未经授权移动执行
钱包资产，或者税费、rebase、黑名单、代理升级等机制使 LP/Swap 会计无法正确
处理时，用户不得覆盖阻断。合约或关键权限变化但尚未重新调查时同样禁止新增
风险。

团队匿名、Meme 属性、没有审计或正式资料、holder/团队/流动性集中、流动性
未锁定、价格与舆情风险，以及系统能够准确识别和处理的增发、暂停、黑名单、
交易税或升级权限，不单独构成技术硬性否决。系统必须展示可取得的证据、信息
缺口和最坏影响，由用户决定拒绝、接受或附带权限与敞口限制接受。

硬性门槛应按能力等级生效：某项失败可以仍允许保存和研究公开数据，但分别
阻止其进入 backtest、paper 或 live。系统必须展示被阻止的等级、原因、证据
和解除条件，不能只显示一个无法解释的总分。

### 7.2 Pool 级资格

每个 `PoolKey` 必须单独检查 PoolManager 部署、配对资产资格、fee、tick
spacing、hook 代码与行为、数据完整性、流动性、可操纵性和策略适用性，并
分别决定是否允许 ingestion、backtest、paper 或 live。

Token 获批不能使相关池自动获批；一个池获批也不能使同币对的其他 PoolKey
自动获批。

### 7.3 持续监控与失效

代码或代理实现变化、管理权限变化、异常增发/解锁、holder 或流动性显著
集中、稳定币脱锚、严重安全事件以及可信风险公告，都应触发告警。达到规定
条件时必须暂停新增风险，并使原批准失效或进入人工复核。

## 8. 当前已确认的目标

- `G-RESEARCH-01`：基于可验证数据产生可复现的历史 LP 策略结果。
- `G-DATA-FREE-01`：V1 的短周期历史研究支持 Robinhood 官方公共 RPC + 用户配置的 Alchemy 免费 endpoint 的零增量成本路径；系统按实测能力路由并记录调用预算，能力不足、额度耗尽或 provider 分歧时 fail closed，不把“免费”当作完整性保证。
- `G-PAPER-01`：在实时虚拟交易中展示真实时序下的信号、持仓、收益和风险。
- `G-STRATEGY-01`：研究中可以比较多个策略版本，但 paper/live 同时只能运行一个人工批准的活动策略版本，系统不得自动切换。
- `G-RECOMMEND-01`：系统可以自动生成、验证和多维排序候选策略参数，但推荐不产生执行权限，最终版本必须由用户人工选择。
- `G-SIGNAL-01`：V1 策略的市场信号只使用当时可得的价格、交易量和流动性分布；价格指标使用经 T053 资格校验的 point-in-time USDG 换算。外部 Token 基本面信息只用于准入与风险，fee/Gas/滑点等只用于成本和执行约束。
- `G-NUMERAIRE-01`：V1 以 USDG 为主要目标和 cash benchmark，不依赖目标 token 上涨证明策略成立；token beta、LP 服务收益和可实现退出价值分别归因。
- `G-ECONOMIC-01`：入场必须依次通过基本面/合约风险闸门、市场状态识别和净经济价值判断，NO_TRADE 是默认合法结果。
- `G-STRATEGY-MAINTAIN-01`：特征、模型、阈值和退出规则通过稳定接口独立版本化，可在实验中替换而不改变账本、风险、执行和审计语义。
- `G-LIFECYCLE-01`：V1 回测完整模拟入场、区间内、区间外等待、撤出、Swap、重建与退出；出区间不是自动退出信号，所有路径必须计入真实库存、费用、Gas、滑点和机会成本。
- `G-UI-01`：提供用于观察、配置、比较、审批、审计和紧急控制的 Web 控制台。
- `G-AUTO-01`：后台不依赖 Web 会话，能够持续运行并从故障中恢复。
- `G-AUTH-01`：策略授权绑定逻辑、参数、代码、PoolKey 和风险版本并持续有效直至人工撤销或关键绑定变化；定期复核只提醒，单笔交易请求仍必须短时有效且不可重放。
- `G-RISK-01`：所有自动操作经过独立、集中且不可绕过的风险检查。
- `G-CONTROL-01`：支持人工暂停、接管和预授权的保护性退出。
- `G-TAKEOVER-01`：人工接管冻结新意图但持续跟踪已广播交易，经状态核对、重新模拟和用户确认后执行风险降低动作；恢复运行是独立人工决定。
- `G-EMERGENCY-01`：市场风险可按版本化策略预授权退出；V1 将目标 token 的完整 5 分钟 USDG 价格跌幅达到 80% 作为策略外应急 AUTO_EXIT 条件。合约、Hook、身份、账本、钱包、nonce、密钥和未知执行语义异常默认锁定通知，不盲目自动退出。
- `G-MARKET-RISK-LEVEL-01`：风险响应采用 WARNING、NO_NEW_RISK、AUTO_EXIT 三级结果；只有后两者限制动作，NO_NEW_RISK 必须绑定明确作用域且不强制退出，AUTO_EXIT 仍须通过最新预执行。
- `G-STRATEGY-SPIKE-01`：目标 token 的完整 5 分钟 USDG 价格涨幅超过 100% 时，V1 策略不再产生增加风险的候选动作并重新评估已有仓位；这不是全局运行状态。
- `G-LOSS-CONTROL-01`：每个完整 LP episode 分别以 USDG 金额和比例限制相对初始资金的亏损及相对历史峰值的回撤；再平衡、重启和资金流不得重置或伪造基准。
- `G-PAUSE-01`：临时异常在核对后可以自动恢复，身份、合约、账本、钱包和密钥类严重异常必须锁定并由用户人工恢复；暂停本身不自动清仓。
- `G-NOTIFY-01`：任一级暂停、升级和解除都通过企业微信 Bot 发送去重通知；Webhook 作为部署秘密管理，通知失败不得影响安全动作。
- `G-CHAIN-01`：V1 只支持 Robinhood Chain，且必须校验实际连接的 chain ID。
- `G-ENV-01`：testnet 负责流程与安全验证，mainnet 负责真实研究、paper 和获批后的真实执行。
- `G-TARGET-01`：目标 token 由用户以 contract address 人工输入并审批。
- `G-TARGET-02`：系统不得自行选择或切换目标 token。
- `G-SCOPE-V1`：V1 围绕一个目标 token 发现多个候选池，但同一时间只运行一个活动池。
- `G-DISCOVER-01`：系统自动发现并完整展示包含目标 token 的 V4 候选池。
- `G-POOL-SELECT-01`：只有通过必要资格检查且经用户单选确认的一个 PoolKey 才能进入策略。
- `G-POOL-SWITCH-01`：系统不得自动切换活动池；切换必须由用户人工确认。
- `G-TOKEN-01`：目标 token 和所有配对 token 分别完成资产资格审批。
- `G-TOKEN-PERM-01`：目标与配对 token 通过 Web 独立管理 HOLD、LP、AUTO_SWAP 和 USDG 敞口；提高权限重新审批，降低权限不自动清仓，CLI 只读。
- `G-TOKEN-LIFECYCLE-01`：Token 审批不按固定日期自动到期，在绑定的技术状态不变时持续有效；关键技术或项目风险变化触发失效或人工复核，定期提醒本身不停止策略。
- `G-ASSET-HARD-GATE-01`：资产硬性门槛不可由人工选择绕过，并按能力等级阻止晋级。
- `G-POOL-01`：每个 PoolKey 独立完成数据、hook、经济性和执行资格审批。
- `G-HOOK-01`：无法理解和验证实际结算影响的 hook 池不得成为 V1 活动池。
- `G-LIVE-01`：V1 必须在 mainnet 的明确授权范围内真实自动完成 LP 与必要的 Swap 操作；只完成回测、testnet 或 paper 不算 V1 完成。
- `G-LIVE-GATE-01`：live 必须按 backtest、testnet、post-testnet paper/shadow、安全复核和人工晋级顺序开放，任何配置不得绕过晋级证据；testnet 前的 preliminary paper 只验证实现，不替代正式 paper/shadow 证据。
- `G-EXEC-01`：每笔真实执行必须经过合约/方法白名单、交易预执行、集中风险检查、资金上限和链上结果核对。
- `G-SIGNER-01`：V1 默认在本地生成全新独立限额 EOA 并直接保存为标准加密 Keystore，原始私钥不显示；可选导入和密码只接受隐藏终端输入，私钥只存在于相关隔离进程内存，重启后必须重新人工解锁。
- `G-FUNDING-01`：执行钱包只接受用户从系统外人工入金，系统不连接或控制主钱包；超出 live 授权范围的余额不得被策略使用，并暂停新增风险等待复核。
- `G-VALUATION-01`：资金与风险统一按 USDG 等值审批和展示并保留原始数量；USDG 估值资格与 USDG 交易 route 分开判断，缺少合格估值时只允许减仓和退出。
- `G-GAS-01`：Gas 储备与 Gas 消耗分别按 USDG 等值审批和记录，同时保留实际 ETH 数量与链上费用证据。
- `G-LIMIT-01`：资金采用全局钱包上限与策略授权上限双层控制，实际许可取更严格值；超限只停止追加与复投，不触发强制退出，下一次重新建仓必须按有效上限缩小投入。
- `G-V4-SIZING-01`：V4 仓位以固定 Range 下的单一 liquidityDelta 等比例缩放，使用 canonical 整数数学、最坏单边库存、Hook BalanceDelta 和原生 ETH Gas 储备校验两边敞口；系统不得为适配限额暗改 Range。
- `G-EXIT-01`：紧急退出只将 LP 资产收回执行钱包并撤销相关授权，不自动向任何外部地址转账。
- `G-RECON-01`：系统重启、RPC 故障、nonce 冲突、交易替换和链重组后仍能恢复真实交易与账本的一致状态，且不会重复执行同一经济意图。

## 9. 已延期到 Paper Trading 阶段的参数决策

以下数值不在 V1 前期开发中提前定案，待系统进入 paper trading 后根据真实观测数据
评审和确定：

- 历史回测、paper 和 live 的具体样本期、置信度、收益/尾部风险阈值及晋级标准；
- 除已确认的 5 分钟极端涨跌规则外，损失/回撤、流动性、Range、策略退出及其他
  经济与风险数值阈值。

延期的是“最终数值”，不是工程机制。前期任务必须实现可配置、不可变版本、时间可用性、
证据留存、回放和审批链路。回测或 preliminary paper 使用的临时值必须标记为
`EXPERIMENTAL_NOT_LIVE_APPROVED`，不得变成隐性默认值。所有 live 所需数值必须在 T093 中用
post-testnet paper/shadow 证据锁定并审批，然后才能进入 T094。这些延期决策不阻塞 T020–T086。
